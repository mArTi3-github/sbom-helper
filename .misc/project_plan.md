# PURL Source Repository Resolver — План развития

## 1. Цель проекта

Веб-приложение и API-сервис для сопоставления Package URL (PURL) с соответствующим репозиторием исходного кода.

Система должна:
- принимать один PURL и возвращать repository URL;
- предоставлять confidence/evidence для результата;
- поддерживать максимально возможное количество экосистем;
- предоставлять удобный REST API;
- предоставлять web UI;
- поддерживать дальнейшее расширение архитектуры и подключение новых резолверов в будущем.

---

## 2. LLM-резолвер

### Описание

Подключение LLM (Large Language Model) в качестве резолвера для поиска репозитория по PURL. LLM может выполнять поиск в интернете и анализировать результаты, что особенно полезно для редких экосистем или пакетов, которые purl2repo не находит.

### Ключевые вопросы

- Какая LLM используется (GPT, Claude, локальная)?
- Как LLM получает доступ к интернет-поиску (search tool, browsing)?
- Какой формат промпта для LLM?
- Как обрабатывать неструктурированный ответ LLM (парсинг repository_url из текста)?
- Какой timeout для LLM-запроса?
- Нужен ли кэш для результатов LLM (отдельно от основного storage)?
- Должен ли LLM-резолвер использоваться как fallback после purl2repo или параллельно?
- Как оценивать confidence для результатов LLM?

### Зависимости

- Пакет для работы с LLM API (openai, anthropic и т.п.)
- Инструмент для веб-поиска (или встроенный browsing в LLM)

## 3. Этапы разработки

### Выполнено

- FastAPI с endpoint `POST /api/v1/resolve`
- GET /health
- GET / (HTML-страница с формой + карточка результата)
- Интеграция purl2repo
- Интеграционные тесты (pytest, hermetic — без сети)
- Docker multi-stage Dockerfile (dev + prod)
- Docker Compose (app + PostgreSQL)
- PostgreSQL для хранения результатов (lookup до purl2repo)
- Service Layer (оркестрация: cache → resolver → store)
- Storage Layer (interface + PostgresCache + InMemoryCache)
- Graceful degradation при отказе БД
- Multi-resolver архитектура (список резолверов в `app.state.resolvers`)
- Application-level PURL validation (purl_utils, packageurl-python)
- Normalized cache keys (`scheme:type/namespace/name`)
- FakeResolver для hermetic тестов
- ADRs: purl2repo, PostgreSQL, purl validation
- **Пакетная обработка PURL** — `resolve_batch()` в service layer (параллельный резолвинг с semaphore)
- **Обогащение SBOM** — приём CycloneDX JSON, резолвинг компонентов, вставка VCS-ссылок
- **Кэширование результатов обогащения** — PURL из обогащённых SBOM автоматически сохраняются в БД (включая компоненты с уже заполненными externalReferences)
- **Database Admin** — веб-интерфейс `/db-admin` для просмотра, редактирования, фильтрации, импорта/экспорта (CSV с `;`-разделителем) и массового удаления записей `resolved_purls`

### Очередные задачи

- **LLM-резолвер** — интеграция LLM как дополнительного резолвера
- **Миграция фронтенда на React** — перевод с Vanilla JS на React для масштабируемости UI (админ-панель, дашборды)
- **Динамический прогресс обогащения SBOM** — отображение в реальном времени прогресса обработки компонентов (WebSocket или SSE)
- **Ручное добавление записей в БД** — добавление записей в БД вручную через веб-интерфейс вкладки db-admin
- **Импорт данных из дампа ecosyste.ms** — подготовка и единоразовый импорт данных в локальную БД из дампа ecosyste.ms (+ предварительная фильтрация дампа)
- **Удаление лишних полей из БД** — анализ и удаление тех полей из локальной БД, которые не используются при практической работе с проектом
- **Импорт ссылок из SBOM** — добавление к разделу "db-admin" функции "Импорт из SBOM" для импорта сопоставлений PURL -> repository_url в локальную БД (по аналогии с функцией "импорт из CSV")
- **Удаление лишних файлов из проекта** — проверка необходимости и достаточности набора файлов в проекте и удаление устаревших/избыточных файлов спецификаций/конфигураций/кода
- **Добавление логирования** — отправка отладочной информации в процессе работы компонентов продукта (резолверов и других компонентов) в лог-файлы
- **Добавление прямых ссылок на скачивание исходных текстов, когда нет репозитория** - для случаев, когда нет ссылки на репозиторий, но есть ссылка на скачивание архива с исходными текстами (такая ситуаация наблюдается, например, для пакетов типа conda в libraries.io) - добавлять прямую ссылку на скачивание. При этом столбец "repository_kind" переформатировать. У этого столбца должно быть 2 возможных значения - "vcs" (для git-репозиториев) или "source_distribution" (для прямых ссылок на скачивание архивов с исходными текстами)
- **Отдельные кнопки Save в настройках** — вместо единой кнопки схоранения нужно добавить отдельные кнопки для каждого подраздела настроек
- **Динамический UI при обогащении SBOM** — присылать отчет о статистике обработки ссылок не в конце обработке, а заполнять его в процессе обработки и динамически обновлять инофрмацию в UI
- **Обертки для инструментов sbom-checker** — добавить обертку в веб-интерфейсе для консольных инструментов для работы со SBOM от ИСП РАН (https://gitlab.community.ispras.ru/sdl-tools/sbom-checker) 
- **Изменить логику проверки доступности github.com** — проверять доступность не при каждом запросе проверки корректности ссылки из локального ДБ, а только для случаев, когда github в ответ на запрос по тестируемой ссылке возвращает ответ, отличный от HTTP 200 
- **Добавление раздела для обработки списка PURL в UI** — кажется, в API была предусмотрена "ручка" /resolve/batch для этого, нужно перепроверить
- **Добавление nginx как reverse-proxy для HTTPS** - если продукт будет усложняться, то логику взаимодействия по HTTPS лучше вынести в отдельный контейнер (reverse-proxy)
- **Добавление асинхронной обработки запросов пользователей** - нужно, чтобы с проектом моги одновременно работать несколько пользователей. Для этого требуется, чтобы задачи выполнялись в асинхронном режиме и выполнение одной задач не блокировало обработку других параллельных запросов
