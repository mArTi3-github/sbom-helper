# Дизайн: поиск точных ссылок на исходные тексты версии PURL

Дата: 2026-11-17
Статус: утверждён

## 1. Зачем

Раздел «Найти ссылку для PURL» сейчас возвращает ссылку на
VCS-репозиторий компонента. Для проверки SBOM и для внешнего сервиса
нужна ссылка на скачивание исходных текстов **конкретной версии**,
указанной в PURL, а не только на репозиторий. GitHub умеет отдавать
архив по тегу и по коммиту:

- `https://github.com/{owner}/{repo}/archive/refs/tags/{tag}.tar.gz`
- `https://github.com/{owner}/{repo}/archive/{sha}.tar.gz`

Пример для `pkg:github/ClickHouse/ClickHouse@23.8.16.40` (или
аналогичного PURL): версия в PURL — `23.8.16.40`, тег в репозитории —
`v23.8.16.40-lts`, коммит — `e143a9039ba36ad0c25f2ed85503f36e88f61063`.
Оформление тегов различается от репозитория к репозиторию, поэтому
сопоставление версии PURL и тега — отдельная детерминированная задача:
список тегов и SHA берётся из репозитория, а версия нормализуется
локально. LLM в первой версии не используется (см. 5.3).

Функция нужна не только в веб-интерфейсе: внешний сервис будет получать
эти ссылки через API, поэтому контракт API должен быть явным и
стабильным, а не побочным эффектом UI.

## 2. Цели

- В разделе «Найти ссылку для PURL» появляется режим «Искать ссылку на
  исходники версии».
- Через API тот же режим включается флагом `find_source_archive: true` в
  `POST /api/v1/resolve/batch`; каждая строка ответа содержит тип
  совпадения, ссылку на архив, тег/SHA и пояснение.
- Точная ссылка — числовая версия в теге совпадает с версией PURL после
  нормализации оформления (`v`-префикс, суффиксы `-lts`, `-release`,
  разделители).
- Близкая ссылка — версия отличается, но лежит в той же ветке
  `major.minor`; фактическая версия тега возвращается клиенту.
- Если близкой ссылки нет, но найден репозиторий — возвращается ссылка
  на репозиторий с пояснением. Если нет и репозитория — явный статус
  `not_found`.
- Результаты поиска сохраняются в БД (включая отрицательные), чтобы
  повторный запрос не запускал поиск с нуля.
- Найденные данные переносятся между стендами существующими скриптами
  бэкапа/восстановления.

## 3. Не-цели

- Не поддерживаем архивные ссылки не-GitHub хостингов (GitLab,
  Bitbucket, self-hosted) в первой версии. Для них возвращается
  `repository_only` с машинно-читаемой причиной `unsupported_host`.
  Архитектура оставляет место для добавления.
- Не добавляем архивные ссылки в обогащение SBOM (externalReferences)
  и в исправление SBOM.
- Не скачиваем архивы, не считаем контрольные суммы и не распаковываем
  их.
- Не делаем отдельную страницу/вкладку, CRUD-API и веб-админ для таблицы
  архивов. Единственная операция управления — `force_refresh` при запросе;
  массовая правка или очистка при необходимости выполняется SQL-запросом
  или восстановлением из бэкапа.
- Не поддерживаем `.zip` и другие форматы архивов как настройку: всегда
  `.tar.gz`.
- Не используем GitHub REST API и GitHub-токен: список тегов берём через
  `git ls-remote`, чтобы не упираться в лимит 60 запросов/час.
- Не используем LLM для выбора тега в первой версии: проверяемое
  детерминированное сопоставление покрывает префиксы, суффиксы и
  разделители; LLM можно добавить позже, если появятся реальные
  неразбираемые схемы тегов.
- Не реализуем автоматическое обновление кэша по TTL и фоновые задания
  для архивов.

## 4. Анти-цели

- Нельзя вернуть близкую ссылку, замаскированную под точную. Тип
  совпадения обязателен в ответе и в БД.
- Нельзя сохранять непроверенную или выдуманную ссылку: URL собирается
  детерминированно из проверенных owner/repo и ref, затем проверяется
  HEAD.
- Нельзя ломать текущий контракт `POST /api/v1/resolve/batch` и семантику
  кэша `resolved_purls` (ключ без версии).
- Нельзя подставлять версию из другой `major.minor` как «близкую».

## 5. Рассмотренные подходы

### 5.1. Где хранить архивные ссылки

1. **Отдельная таблица с ключом «канонический PURL с версией» (выбран).**
   Аддитивна: не трогает `resolved_purls`, его ключ без версии, четыре
   колонки и все текущие инварианты. Позволяет хранить несколько версий
   одного PURL, отрицательные результаты и признак типа совпадения.
   Минус — новая таблица и новая поверхность (API, бэкап).
2. **Расширить `resolved_purls` nullable-колонками.** Меньше кода, но у
   одной versionless-строки может быть много версий. Пришлось бы писать
   версионные строки в ту же таблицу, смешивая два вида записей в
   обычном резолве, `ON CONFLICT (purl)`, админке и CSV. Ломает текущий
   контракт.
3. **Отдельная таблица с ключом `(repository_url, version)`.** Логически
   точнее, но требует стабильной нормализации `repository_url`
   (редиректы, `.git`, схема) и сначала гарантированного репозитория;
   сложнее инвалидация и поиск.

### 5.2. Как получать теги

1. **GitHub REST API `/tags` (отклонён).** Анонимный лимит 60
   запросов/час; для массовых запросов непригоден, нужен токен, а
   поддержка токена из проекта удалялась.
2. **`git ls-remote --tags <repo>` (выбран).** Уже используется `git` в
   `url_validator.py`; одна команда отдаёт все теги и SHA коммитов без
   API-лимита. Работает для любого git-хостинга, что оставляет путь к
   расширению.
3. **Только LLM с web-search (отклонён).** Дорого, недетерминированно,
   дороже для повторных запросов; оставлен как fallback.

### 5.3. Как сопоставлять версию и тег

1. **Только LLM (отклонён).** Не даёт воспроизводимости и не позволяет
   дёшево проверить точное совпадение.
2. **Детерминированные правила по списку тегов (выбран).** Список тегов
   и SHA получаем через `git ls-remote`; числовую версию выделяем из
   тега с учётом префиксов, суффиксов и разделителей, затем сравниваем
   с версией PURL. Покрывает `v23.8.16.40-lts`, `rel_23_8_16_40`,
   `release-1.2.3`, `v1.2.3-rc4` и подобные схемы.
3. **Детерминированно, затем LLM (отложен).** LLM мог бы выбирать тег,
   но при требовании проверять версию по `git ls-remote` он не может
   добавить совпадение там, где детерминированный поиск его не нашёл:
   подтверждённый тег либо уже классифицируется детерминированно, либо
   не проходит проверку. Ценность сводится к выбору между одинаково
   точными тегами, поэтому LLM исключён из первой версии.

## 6. Дизайн

### 6.1. Ключ кэша и нормализация PURL

Новый помощник в `purl_utils`:

- `normalize_with_version(components) -> str` — канонический PURL,
  включающий `version`, но **без** `qualifiers` и `subpath`.
  Пример: `pkg:github/ClickHouse/ClickHouse@23.8.16.40`.
- `PurlComponents.version` берётся из `validate()`; для режима поиска
  архивов версия обязательна.

Почему без qualifiers/subpath: архив исходников определяется
репозиторием и версией; qualifiers (например, `arch=amd64`) и subpath к
содержимому архива не относятся и только размножили бы записи.

### 6.2. Схема БД

Новая таблица в `src/purl_resolver/storage/schema.sql`:

```sql
CREATE TABLE IF NOT EXISTS purl_source_archives (
    purl               TEXT PRIMARY KEY,
    version            TEXT NOT NULL,
    match_type         TEXT NOT NULL,  -- exact | near | repository_only | not_found
    reason             TEXT,           -- машинно-читаемая причина (см. 6.4)
    archive_url        TEXT,           -- основная ссылка; NULL для repository_only/not_found
    archive_url_commit TEXT,           -- ссылка по коммиту, если известен SHA
    matched_ref        TEXT,           -- тег или SHA
    matched_ref_type   TEXT,           -- tag | commit
    matched_version    TEXT,           -- нормализованная версия тега (для near)
    repository_url     TEXT,           -- репозиторий, по которому строился архив
    resolver           TEXT NOT NULL,  -- git-tags
    resolved_at        TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_purl_source_archives_match_type
    ON purl_source_archives (match_type);
```

Индекс на `match_type` нужен для будущей диагностики/фильтрации и не
мешает вставкам.

Таблица создаётся на старте вместе с остальными в `create_pool()`.

### 6.3. Слой хранения

Отдельный интерфейс, чтобы не раздувать `Storage` (у него уже восемь
методов и своя семантика):

```python
@dataclass
class SourceArchiveRow:
    purl: str
    version: str
    match_type: str
    reason: str | None = None
    archive_url: str | None = None
    archive_url_commit: str | None = None
    matched_ref: str | None = None
    matched_ref_type: str | None = None
    matched_version: str | None = None
    repository_url: str | None = None
    resolver: str = ""
    resolved_at: str = ""


class SourceArchiveStorage(ABC):
    async def lookup_archive(self, purl: str) -> SourceArchiveRow | None: ...
    async def store_archive(self, row: SourceArchiveRow) -> None: ...
```

Реализации:

- `PostgresSourceArchiveStorage` — `SELECT`/`INSERT ... ON CONFLICT (purl)
  DO UPDATE`, `resolved_at = NOW()`.
- `InMemorySourceArchiveStorage` — словарь, используется при недоступной
  PostgreSQL, чтобы приложение работало без БД.

Хранилище создаётся в `main.py` рядом с `PostgresCache`; при падении
PostgreSQL используется in-memory реализация, как сейчас для
`resolved_purls`.

### 6.4. Типы совпадений и причины

`match_type`:

| Значение | Значение для клиента | `archive_url` |
|---|---|---|
| `exact` | версия совпала точно | есть |
| `near` | взята ближайшая версия в той же `major.minor` | есть |
| `repository_only` | архив не найден, есть только репозиторий | NULL |
| `not_found` | не найден ни архив, ни репозиторий | NULL |

`no_version` не хранится в БД: PURL без версии не доходит до поиска
архива. В ответе API для такой строки `source_archive_match:
"no_version"`, `source_archive_reason: "no_version"`.

`reason` (машинно-читаемый, стабильный). Причины взаимоисключающие,
проверяются сверху вниз, первая подходящая попадает в ответ:

1. `no_version` — в PURL нет версии;
2. `non_numeric_version` — версия PURL не содержит числового ряда
   (например, `@main`, `@latest`), сопоставление по версиям невозможно;
3. `no_repository` — репозиторий не найден;
4. `unsupported_host` — репозиторий не GitHub;
5. `git_error` — `git ls-remote` не удался (сеть, приватный репозиторий,
   таймаут);
6. `archive_check_failed` — собранная архивная ссылка не прошла HEAD;
7. `no_matching_tag` — теги получены, но ни точного, ни близкого
   совпадения нет.

Для `exact` и `near` `reason` = NULL. `no_version` и
`non_numeric_version` в БД не сохраняются как отдельные строки (см.
6.8), но возвращаются в ответе API.

### 6.5. Сопоставление версий

Вход: `version` из PURL; список тегов из `git ls-remote --tags`
(включая строки `refs/tags/<tag>` и `refs/tags/<tag>^{}`, если тег
аннотированный — распакованный SHA коммита берём из `^{}`).

Нормализация имени тега:

1. Взять последний сегмент `refs/tags/<tag>`.
2. Разбить имя на чередующиеся группы цифр и нецифровых символов.
3. Выбрать самую длинную цепочку групп цифр, разделённых разделителями
   без букв (`.`, `-`, `_`, `/`, `+`). Это числовая версия тега.
4. Всё, что стоит до цепочки, — префикс (`v`, `release`, имя проекта);
   всё, что после, — суффикс (`lts`, `stable`, `rc1`, хеш). Префикс
   игнорируется; суффикс участвует только в проверке точности, если он
   есть у версии PURL.

Примеры: `v23.8.16.40-lts` → `(23, 8, 16, 40)`, суффикс `lts`;
`rel_23_8_16_40` → `(23, 8, 16, 40)`; `release-1.2.3` → `(1, 2, 3)`;
`v1.2.3-rc4` → `(1, 2, 3)`, суффикс `rc4` (буквы `rc` разрывают
цепочку). Если в теге нет цифр, он не участвует в сопоставлении.

Нормализация версии PURL: обрезать пробелы, выделить числовую версию и
нечисловой суффикс тем же способом (например, `2.0.0-rc1` → `2.0.0` +
`rc1`). Числовые кортежи сравниваются покомпонентно; недостающие
компоненты дополняются нулями, поэтому `1.2` и `1.2.0` считаются одной
версией. Если в версии PURL нет цифр, результат — `non_numeric_version`.

**Точное совпадение (`exact`):**

- числовой кортеж тега равен числовому кортежу версии PURL (с
  дополнением нулями);
- если у версии PURL есть нечисловой суффикс, он должен совпасть с
  нормализованным суффиксом тега (без учёта регистра и разделителей);
- если у версии PURL суффикса нет, тег может иметь любой суффикс
  (`v23.8.16.40-lts` подходит для `23.8.16.40`).

**Выбор при нескольких точных тегах** (детерминированный приоритет):

1. тег без пре-релизных маркеров (`rc`, `alpha`, `beta`, `pre`, `dev`,
   `snapshot`, `nightly`) — раньше, чем с ними;
2. более короткое имя тега;
3. лексикографически меньшее имя.

Если точных несколько, в `warnings` строки добавляется пояснение, какой
тег выбран.

**Близкое совпадение (`near`):**

- рассматриваются только теги той же `major.minor` (первые две
  компоненты; недостающие компоненты считаются нулями);
- теги с пре-релизными маркерами исключаются, если версия PURL сама не
  содержит такого маркера;
- кандидат с равным числовым кортежем, но несовпавшим суффиксом
  (например, PURL `2.5.0-rc1` и тег `v2.5.0`), считается близким, а не
  точным;
- приоритет выбора: сначала равный числовой кортеж (ближайшее
  совпадение), затем наибольшая версия **ниже** целевой, затем
  наименьшая версия **выше** целевой;
- `matched_version` — нормализованная версия выбранного тега,
  возвращается клиенту и сохраняется в БД.

Если в той же `major.minor` ничего нет, `near` не подставляется; итог —
`repository_only` с причиной `no_matching_tag`.

**LLM в первой версии не используется.** Причина в 5.3: при требовании
проверять выбранный тег по `git ls-remote` и по тем же правилам версии
LLM не может добавить совпадение там, где детерминированный поиск его
не нашёл. Если позже появится реальная схема тегов, которую нельзя
разобрать детерминированно, LLM можно добавить отдельным решением.

### 6.6. Получение тегов через git

Новый модуль `src/purl_resolver/source_archive/git_tags.py`:

- запускает `git ls-remote --tags <repository_url>` через
  `asyncio.create_subprocess_exec`;
- окружение: `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=/bin/true` (или
  аналог), чтобы не зависнуть на запросе пароля;
- таймаут — новая настройка `source_archive_timeout` (по умолчанию 30 с);
  по таймауту процесс убивается, результат — `git_error`;
- допустимы только `http(s)` URL с непустым hostname; иначе
  `unsupported_host`;
- разбирает обе строки аннотированных тегов и сохраняет пары
  `(tag_name, peeled_commit_sha | None)`;
- ограничивает объём вывода (например, 5 МБ) и число тегов (например,
  50 000) с предупреждением, чтобы не съесть память на гигантских
  репозиториях.

### 6.7. Построение ссылки GitHub

Новый модуль `src/purl_resolver/source_archive/github.py`:

- принимает `repository_url`, извлекает host и путь;
- поддерживает только `github.com` (и `www.github.com`), путь строго
  `/{owner}/{repo}`; хвостовой `.git` и `/` отбрасываются;
- `owner`/`repo` проверяются регуляркой `^[A-Za-z0-9_.-]+$`;
- ссылка по тегу:
  `https://github.com/{owner}/{repo}/archive/refs/tags/{tag}.tar.gz`,
  тег кодируется с сохранением `/` (теги с косой чертой допустимы);
- ссылка по коммиту:
  `https://github.com/{owner}/{repo}/archive/{sha}.tar.gz`;
- SHA — только 40 hex-символов.

Проверка ссылки: HTTP HEAD с `follow_redirects=True` и таймаутом
`source_archive_timeout`; успех — статус < 400. GitHub редиректит
архив на `codeload.github.com`; следование редиректам обязательно.
Ссылка по тегу — основная; `archive_url_commit` заполняется, если из
`git ls-remote` известен SHA коммита аннотированного тега. Клиент может
выбрать неизменяемую commit-ссылку, но основной в ответе остаётся
tag-ссылка.

### 6.8. Сервис

Новый `SourceArchiveService` в `src/purl_resolver/source_archive/service.py`:

```python
class SourceArchiveService:
    async def lookup(
        self, purl: str, repository_url: str | None, force_refresh: bool = False
    ) -> SourceArchiveResult: ...

    async def enrich_many(
        self,
        purls: list[str],
        repository_urls: list[str | None],
        force_refresh: bool = False,
    ) -> list[SourceArchiveResult]: ...
```

Порядок для одного PURL:

1. `validate(purl)`; нет версии → `no_version` (в БД не пишем;
   `match_type = no_version`).
2. Выделить числовую версию; цифр нет → `non_numeric_version` (в БД не
   пишем; `match_type = repository_only`, если `repository_url` есть,
   иначе `not_found`).
3. `normalize_with_version()` → ключ.
4. Если `force_refresh = false` — `lookup_archive(key)`. При попадании:
   - если текущий `repository_url` не пуст и отличается от сохранённого
     в строке — запись считается устаревшей, идём дальше и перезаписываем
     её (репозиторий сменился);
   - иначе вернуть строку с `cached=True`. Если текущий репозиторий не
     найден (`None`), сохранённая архивная ссылка всё равно возвращается:
     она не зависит от доступности репозитория в данный момент.
5. Если `repository_url` пуст → `not_found` / `no_repository`; сохранить.
6. Разобрать GitHub owner/repo; не GitHub → `repository_only` /
   `unsupported_host`; сохранить.
7. `git ls-remote --tags`; ошибка → `repository_only` / `git_error`;
   сохранить.
8. Точное совпадение → HEAD; успех → `exact`; неудача →
   `repository_only` / `archive_check_failed`; сохранить.
9. Близкое совпадение → HEAD; успех → `near`; неудача →
   `repository_only` / `archive_check_failed`; сохранить.
10. Иначе `repository_only` / `no_matching_tag`; сохранить.
11. Сохранение в БД — best-effort: ошибка storage логируется и не ломает
    ответ.

Кэшируются все четыре типа (`exact`, `near`, `repository_only`,
`not_found`). `force_refresh=true` игнорирует кэш архивов, выполняет
поиск заново и перезаписывает строку. Разрешение репозитория при этом
идёт обычным путём (со своим versionless-кэшем): `force_refresh` не
обходит кэш `resolved_purls`.

### 6.9. API

Расширение существующего эндпоинта:

```json
{
  "purls": ["pkg:github/ClickHouse/ClickHouse@23.8.16.40"],
  "find_source_archive": true,
  "force_refresh": false
}
```

- `find_source_archive` — bool, по умолчанию `false`; при `false`
  поведение и ответ полностью прежние (новые поля отсутствуют или
  `null`).
- `force_refresh` — bool, по умолчанию `false`; действует только при
  `find_source_archive: true`.

Как работает `force_refresh`:

- без флага архивная строка ищется в `purl_source_archives`; при
  попадании возвращается сохранённый результат (`source_archive_cached:
  true`) без `git ls-remote` и HEAD;
- с флагом кэш архивов для этих PURL игнорируется: поиск выполняется
  заново, строка перезаписывается;
- кэш репозиториев `resolved_purls` флаг не обходит — ссылка на
  репозиторий берётся обычным путём;
- типичные случаи: тег появился после предыдущего запроса; раньше был
  найден только `near`/`repository_only`/`not_found`; нужно гарантированно
  свежее состояние перед выдачей внешнему потребителю.

Строка ответа при включённом режиме:

```json
{
  "purl": "pkg:github/ClickHouse/ClickHouse@23.8.16.40",
  "repository_url": "https://github.com/ClickHouse/ClickHouse",
  "warnings": ["Multiple exact tags matched; chose 'v23.8.16.40-lts'"],
  "resolver": "purl2repo",
  "found_by": "resolver",
  "resolved_at": "2026-11-17T12:00:00Z",
  "error": null,
  "source_archive_url": "https://github.com/ClickHouse/ClickHouse/archive/refs/tags/v23.8.16.40-lts.tar.gz",
  "source_archive_commit_url": "https://github.com/ClickHouse/ClickHouse/archive/e143a9039ba36ad0c25f2ed85503f36e88f61063.tar.gz",
  "source_archive_commit_sha": "e143a9039ba36ad0c25f2ed85503f36e88f61063",
  "source_archive_match": "exact",
  "source_archive_reason": null,
  "source_archive_ref": "v23.8.16.40-lts",
  "source_archive_ref_type": "tag",
  "source_archive_matched_version": "23.8.16.40",
  "source_archive_resolver": "git-tags",
  "source_archive_cached": false,
  "source_archive_resolved_at": "2026-11-17T12:00:00Z"
}
```

Семантика:

- `source_archive_url` — основная ссылка; NULL для
  `repository_only`/`not_found`/`no_version`.
- `source_archive_match` — одно из `exact`, `near`, `repository_only`,
  `not_found`, `no_version`.
- `source_archive_reason` — стабильный код причины (см. 6.4) или NULL.
- `source_archive_ref_type` — `tag` или `commit`; NULL, если ссылки нет.
- `source_archive_matched_version` — фактическая версия тега; для
  `near` отличается от версии PURL.
- `source_archive_cached` — данные взяты из БД, а не получены сейчас.
- `source_archive_resolved_at` — время сохранения результата.

Ошибка одной строки (`invalid_purl`, `upstream_error` в репозитории) не
ломает запрос; архивные поля в такой строке — `null`. Ошибки
архивного поиска не превращаются в HTTP 5xx: это per-row статус.

Существующие коды ошибок (`batch_too_large`, `network_unavailable`,
422) не меняются.

### 6.10. Настройки

В `AppSettings` добавляются:

- `source_archive_timeout: float = 30.0`, диапазон 1–300 — таймаут
  `git ls-remote` и HEAD-проверки архивной ссылки;
- `source_archive_concurrency: int = 5`, диапазон 1–50 — число
  параллельных архивных поисков в одном batch-запросе (отдельный
  семафор; не заменяет `batch_semaphore_limit`, который ограничивает
  разрешение репозиториев).

Латентность: архивный поиск синхронный. Худший случай на строку —
`source_archive_timeout` на `git ls-remote` плюс HEAD-проверка. При
`source_archive_concurrency = 5` и большом батче запрос может быть
долгим; внешнему сервису рекомендуется отправлять в режиме архивов
небольшие батчи. Асинхронные задания для архивов — вне первой версии
(см. не-цели).

На странице «Настройки» добавляются поля таймаута и параллелизма в
существующей секции, связанной с резолверами/сетью; точное место — на
усмотрение исполнителя.

### 6.12. Бэкап и восстановление

`scripts/db_backup.sh` дополнительно выгружает
`purl_source_archives` в отдельный файл с тем же временным суффиксом:

- `backups/sbom_purls_YYYYmmdd-HHMMSS.csv.gz` — как сейчас;
- `backups/sbom_source_archives_YYYYmmdd-HHMMSS.csv.gz` — новый.

Колонки нового файла строго в порядке:
`purl,version,match_type,reason,archive_url,archive_url_commit,matched_ref,matched_ref_type,matched_version,repository_url,resolver,resolved_at`;
сортировка по `purl`; `PGTZ=UTC`.

Поведение флагов:

- `-o FILE` / `--output FILE` задаёт путь для файла `resolved_purls`;
  архивный файл пишется рядом с суффиксом `.source_archives` перед
  `.csv.gz` (для `out.csv.gz` → `out.source_archives.csv.gz`). Без
  `-o` оба файла получают один и тот же временной суффикс
  `YYYYmmdd-HHMMSS`.
- `--keep N` считает наборы (пары файлов с одинаковым временным
  суффиксом) и удаляет старые наборы целиком, оставляя `N` последних;
  одиночные файлы без пары удаляются по тому же временному суффиксу.

`scripts/db_restore.sh`:

- принимает один или два файла; таблица определяется по заголовку
  (точное совпадение со списком колонок), поэтому старые одиночные
  бэкапы `resolved_purls` продолжают работать;
- `--mode merge` (по умолчанию) для новой таблицы: существующие `purl`
  на стенде не перезаписываются, добавляются отсутствующие (та же
  семантика, что и для `resolved_purls`);
- `--mode replace`: `TRUNCATE purl_source_archives` и вставка из
  staging в одной транзакции; пустой файл для replace отклоняется;
- счётчики `inserted`/`skipped`/`total` печатаются отдельно по каждой
  таблице;
- staging-таблица создаётся через
  `LIKE purl_source_archives INCLUDING DEFAULTS` и удаляется через trap.

В `DbBackupHelp.vue` и `README.md` добавляются строки о втором файле и о
том, что restore принимает оба файла.

## 7. Проверка

Backend:

- unit-тесты нормализации версий и выбора тега: `v`-префикс,
  `-lts`/`-release`, `v23.8.16.40-lts` для `23.8.16.40`,
  `rel_23_8_16_40`, `release-1.2.3`, пре-релизы, несколько точных
  тегов (приоритет), близкая версия ниже/выше, равный числовой кортеж
  с несовпавшим суффиксом (`2.5.0-rc1` vs `v2.5.0`),
  `1.2` vs `v1.2.0`, запрет перехода в другую `major.minor`,
  нечисловая версия (`@main` → `non_numeric_version`), тег без цифр;
- парсинг `git ls-remote --tags` (аннотированные и легковесные теги,
  `^{}`);
- построение GitHub URL: `.git`, хвостовой `/`, не-GitHub, тег с `/`,
  невалидные owner/repo, не-40-hex SHA;
- сервис с подменёнными git/HTTP: `exact`, `near`, `repository_only`,
  `not_found`, `no_version`, `non_numeric_version`, `git_error`,
  `archive_check_failed`, `no_matching_tag`;
- кэш: попадание, `force_refresh`, сохранение отрицательных
  результатов, перезапись при смене `repository_url`, возврат
  сохранённой ссылки при временно недоступном репозитории,
  недоступная БД;
- API: `find_source_archive: false` не меняет ответ; `true` добавляет
  поля; `invalid_purl` не ломает батч;
- скрипты: `bash -n scripts/db_backup.sh scripts/db_restore.sh` и ручной
  сценарий на docker compose (бэкап → merge → replace, оба файла,
  `-o`/`--keep`).

Frontend:

- `npm --prefix frontend run test` — `PurlResolver.test.ts`: чекбокс,
  новые колонки, бейджи `exact`/`near`/`repository_only`/`not_found`/
  `no_version`, отсутствие новых колонок при выключенном режиме;
- тест настроек для новых таймаута и параллелизма;
- `npm --prefix frontend run build`.

Полный прогон перед завершением — по `AGENTS.md`:
`.venv/bin/python -m pytest -q`; при сетевых падениях только e2e —
`SKIP_E2E=1 .venv/bin/python -m pytest -q`.
