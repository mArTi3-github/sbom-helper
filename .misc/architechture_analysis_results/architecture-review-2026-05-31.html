Extract CSV import/export from router

Strong in-process
src/purl_resolver/router.py · lines 208–353

Before

router.py
├─ resolve_endpoint
├─ resolve_sbom_endpoint
├─ import_csv_endpoint ← 90 lines of CSV parsing
├─ export_csv_endpoint ← 55 lines of CSV writing
└─ db_admin_page

CSV format logic, BOM handling, field mapping, error collection — all inline in HTTP handlers.

After

router.py
├─ resolve_endpoint
├─ resolve_sbom_endpoint
├─ import_csv_endpoint ← 15 lines, calls csv_io
├─ export_csv_endpoint ← 15 lines, calls csv_io
└─ db_admin_page
csv_io.py ← new module
├─ parse_import(text, strategy) → (rows, errors)
├─ render_export(rows) → str
└─ detect_delimiter(text) → str

Problem: CSV parsing, BOM handling, delimiter detection, field mapping, error collection, and skip-existing strategy logic are all inlined in two HTTP handlers (~145 lines total). This logic has no business knowing about HTTP.

Solution: Extract a csv_io module with pure functions: parse_import(), render_export(). Router calls these and wraps results in HTTP responses.

  • • Leverage: one interface, reusable for CLI import/export
  • • Locality: CSV format bugs concentrate in csv_io, not router
  • • Testability: test CSV parsing without FastAPI TestClient

Type the upsert_many interface

Strong in-process
storage/interface.py:64 · storage/inmemory.py:105–154 · storage/postgres.py:239–305

Before

upsert_many(rows: list[dict[str, object]])
→ tuple[int, int]

// each implementation manually:
row.get("purl") → str(row.get(...))
json.loads(row.get("evidence"))
json.loads(row.get("warnings"))
× 30 lines of parsing per implementation

After

@dataclass
class UpsertRow:
  purl: str
  repository_url: str
  evidence: list[str]
  warnings: list[str]
  ...

upsert_many(rows: list[UpsertRow])
→ tuple[int, int]

// implementations read typed fields directly
× 0 lines of manual parsing

Problem: upsert_many takes untyped dict[str, object]. Both InMemoryCache and PostgresCache independently parse each field with str(row.get(...)) and json.loads() — ~30 lines of duplicated parsing per implementation. Bugs hide in the parsing, not the storage.

Solution: Define an UpsertRow dataclass in storage/interface.py. Implementations read typed fields directly. Router constructs UpsertRow from CSV dicts once.

  • • Leverage: one typed interface, two implementations stop duplicating parsing
  • • Locality: field mapping lives in one place (csv_io → UpsertRow)
  • • Deletion test: deleting the dict forces each caller to re-implement parsing

Problem: The same purl→repository mapping exists as 4 types across 3 files. The router copies fields between PurlRow and PurlRowResponse in a 10-field 1:1 mapping. Each boundary forces a manual field copy.

Solution: Define one canonical PurlRecord dataclass. Use thin adapters at boundaries (Pydantic model for API, asyncpg row reader for DB). Eliminate PurlRowResponse as an alias.

  • • Leverage: one type, adapters handle boundary translation
  • • Locality: field additions propagate to one type, not four
  • • Caution: touches many files; ADR-0002 may need revisiting

Split Storage into Cache + Repository

Worth exploring ports & adapters
storage/interface.py · storage/inmemory.py · storage/postgres.py

Before

Storage (ABC)
7 abstract methods
lookup() ← cache
store() ← cache
list_purls() ← admin
count_purls() ← admin
update_purl() ← admin
delete_purls() ← admin
upsert_many() ← admin

After

ResolutionCache (ABC)
2 methods
lookup()
store()
PurlRepository (ABC)
5 methods
list_purls()
count_purls()
update_purl()
delete_purls()
upsert_many()

Problem: The Storage ABC mixes two concerns: resolution cache (2 methods) and admin CRUD (5 methods). The resolution pipeline only needs lookup/store, but must satisfy the full 7-method interface. InMemoryCache implements admin methods it doesn't need for fallback.

Solution: Split into ResolutionCache (lookup, store) and PurlRepository (list, count, update, delete, upsert). Each implementation can satisfy one or both.

  • • Leverage: callers see only the interface they need
  • • Locality: admin logic vs. cache logic separated at the seam
  • • Caution: two adapters needed to justify the split; currently both implementations satisfy both interfaces

Centralize PURL normalization

Speculative in-process
purl_utils/ · service.py · router.py · sbom/enricher.py · sbom/reporter.py

Problem: safe_normalize is called in 5 different modules. Every caller must remember to normalize — a missed call means a cache miss or incorrect storage key. Normalization is a cross-cutting concern threaded through every layer individually.

Solution: Normalize once at the storage boundary (normalize on write, normalize on read) or in the service layer. Callers pass raw PURLs; normalization happens internally.

  • • Leverage: one normalization point, callers stop worrying about it
  • • Locality: normalization bugs concentrate at one seam
  • • Caution: the resolver needs the original PURL (not normalized) for version-specific lookups; must preserve both forms

Top recommendation

Extract CSV import/export from router — the strongest candidate. The 145 lines of CSV parsing, BOM handling, delimiter detection, field mapping, error collection, and skip-existing strategy are all inlined in HTTP handlers. Extracting a csv_io module would make this logic testable without FastAPI, reusable for CLI, and concentrated in one place. This is the change with the highest leverage-to-effort ratio.

Tackle this alongside typing the upsert_many interface — the untyped dict[str, object] in upsert_many is the root cause of duplicated parsing in both InMemoryCache and PostgresCache. An UpsertRow dataclass would collapse ~60 lines of duplicated code.
