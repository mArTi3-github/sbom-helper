Общее описание назначения и структуры проекта sbom-helper доступно в specs/INDEX.md (и в файлах, на которые есть ссылки в INDEX.md). specs/META.md определяет формат и правила обновления спецификаций.

Общие правила работы описаны в .misc/PROJECT_WORKFLOW.md.

Термины, используемые в текущем проекте, описаны в файле CONTEXT.md.

Разработка ведется в ОС Ubuntu с использованием IDE VS Code и расширения Kilo Code.

## Процесс разработки

Для планирования, внедрения и тестирования изменений используй скиллы из набора "superpowers". Для подключения нужных скиллов используй MCP-сервер superpowers-mcp.
Если ты не нашел скилл - не надо пытаться имитировать ответ, пытаясь предполагать, какая информация была заложена в скилле. Обратись к mcp-серверу superpowers-mcp для получения нужных скиллов.

### Границы процесса

- Небольшие изменения (1–3 файла, без изменения контрактов, моделей данных и поведения на границах слоёв) можно реализовывать напрямую: прочитать затрагиваемый код и spec, написать или обновить тесты, внести правку. Полный цикл brainstorming → writing-plans → subagent-driven-development для таких правок не нужен.
- Изменения, затрагивающие несколько слоёв, контракты API, модели опций или данных, публичное поведение либо структуру спецификаций, проходят полный цикл: brainstorming → writing-plans → subagent-driven-development → finishing-a-development-branch.
- Если объём работы вырос по ходу задачи, остановись и перейди на более полный процесс, а не продолжай в упрощённом режиме.

### Ветка и рабочее пространство

Разработка ведётся напрямую в ветке `main` в текущем checkout. Worktree не создаём; изоляция рабочего пространства для параллельных задач не требуется.

### Проверки

Backend (в `.venv`):

```bash
.venv/bin/python -m pytest -q
```

Сначала запускай полный набор тестов. Если падают только e2e-тесты из-за недоступности внешней сети (например, таймауты ecosyste.ms в `tests/e2e/`), повтори прогон с `SKIP_E2E=1`:

```bash
SKIP_E2E=1 .venv/bin/python -m pytest -q
```

Frontend:

```bash
npm --prefix frontend run test
npm --prefix frontend run build
```

### Спецификации и документы решений

`specs/` и `docs/superpowers/` дополняют друг друга:

- `specs/` — актуальная документация проекта: что система делает сейчас, её контракты, инварианты и принятые решения. Это источник истины при расхождениях.
- `docs/superpowers/specs/` и `docs/superpowers/plans/` — обоснование и рекомендации по выполнению конкретных задач модернизации: какой вариант выбран, почему и как его внедрять.

Оба набора документов хранятся в git.

**Обновление спецификаций — отдельный шаг после завершения всех правок в коде.** Сначала внеси изменения и проверь их тестами, затем отдельным этапом обнови `specs/`. Для правок в `specs/` руководствуйся набором скиллов `vibespec` (`vibespec-update`, `vibespec-check` и другие подходящие скиллы набора). Перед структурными изменениями сначала читай соответствующий spec из `specs/`.

### Модели субагентов

Выбирай модель только из реально доступных моделей; проверяй доступность через `agent_manager_models` и не предполагай доступность по названию. В текущем окружении доступен провайдер deepseek. Если выбранная модель недоступна или соединение с ней сбрасывается, используй модель текущей сессии — наследование модели сессии допустимо.

### Расположение helper-скриптов superpowers

Helper-скрипты скиллов (не сами скиллы, а утилиты вроде `task-brief`, `review-package`) лежат в `~/.superpowers-mcp/skills/skills/<skill-name>/scripts/`:

- `~/.superpowers-mcp/skills/skills/subagent-driven-development/scripts/` — `task-brief PLAN N [OUTFILE]` (извлекает текст задачи в файл), `review-package BASE HEAD` (готовит diff для ревьюера), `sdd-workspace`
- `~/.superpowers-mcp/skills/skills/brainstorming/scripts/` — `start-server.sh`, `stop-server.sh` (для visual companion)
- `~/.superpowers-mcp/skills/skills/systematic-debugging/find-polluter.sh`

Перед использованием скилла `subagent-driven-development` сначала запускай `task-brief` для генерации брифа задачи и `review-package BASE HEAD` для генерации diff-файла перед ревью.

## Среда и инструменты

Для запуска кода на python используй виртуальное окружение .venv. Также передавай эту инструкцию по использованию виртуального окружения суб-агентам при необходимости, чтобы они не пытались запускать код напрямую. При необходимости установки новых python-модулей также вызывай pip внутри виртуального окружения.

Для получения актуальной документации библиотек и фреймворков проекта (FastAPI, Pydantic, asyncpg, httpx, pytest, vue.js и др.) используй MCP-сервер context7. Доступны инструменты: context7_resolve-library-id и context7_query-docs.

Для исследования проекта:

- документация в папке `specs` — основной источник сведений о поведении и контрактах;
- MCP-сервер codebase-memory-mcp (название проекта: "home-administrator-Desktop-projects-sbom-helper") — для обзорного исследования архитектуры и связей между модулями; для точечных правок в известных файлах обычный поиск по коду быстрее и надёжнее. Обновляй индекс перед использованием, только если есть основания полагать, что код менялся после прошлой индексации (например, после крупного рефакторинга или переключения ветки); между запросами одной серии повторно не индексируй.
- механизм индексирования Kilo Code — для поиска по коду;
- Project Memory — инструменты kilo_memory_recall (поиск ранее сохранённых фактов, решений, ограничений, контекста сессий) и kilo_memory_save (сохранение важных фактов о проекте для переиспользования в будущих сессиях).
