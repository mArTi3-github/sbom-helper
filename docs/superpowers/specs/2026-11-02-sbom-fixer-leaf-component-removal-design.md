# «Исправить SBOM» — удаление компонентов-листьев без PURL, с некорректным PURL и без version: дизайн

Документ дополняет `2026-10-26-sbom-fixer-design.md`, `2026-10-29-sbom-fixer-optional-fields-design.md`, `2026-10-29-sbom-fixer-rule-help-design.md`, `2026-11-01-sbom-fixer-base-fixes-group-design.md` и `2026-11-01-sbom-fixer-licenses-design.md` в части состава статических правил, модели опций и интерфейса. При расхождениях приоритет у этого документа.

## 1. Задача и зачем

Требования ФСТЭК (`.misc/addictional_materials/sbom_description_fstec.md`, таблица П.5) делают поля `purl` и `version` обязательными для каждого компонента. В реальных SBOM встречаются компоненты-листья, у которых `purl` отсутствует или пуст, `purl` заполнен с нарушением спецификации Package URL, либо отсутствует `version`. Такие записи невозможно корректно обогатить и они заведомо не соответствуют требованиям.

Нужно добавить в подраздел **«Правки массива components[]»** три пункта:

1. «Удалить компоненты-листья без PURL» (по умолчанию выключено);
2. «Удалить компоненты-листья с некорректным PURL» (по умолчанию выключено);
3. «Удалить компоненты-листья без version» (по умолчанию выключено).

Удаляются только компоненты без собственных подкомпонентов: если у компонента есть непустой массив `components`, он сохраняется независимо от своих `purl`/`version`. Так контейнеры с подкомпонентами не исчезают из SBOM вместе с описанием вложенных компонентов.

Пункт «Привести все PURL к строчному регистру» в этой задаче не реализуется: регистр в `namespace`/`name`/`version` значим для ряда экосистем, и такое преобразование может сделать PURL неканоничным.

## 2. Цели, не-цели и анти-цели

### Цели

- Три новых статических правила с отдельными rule id, флагами и строками статистики.
- Удаление только листьев; контейнеры с непустым `components` не удаляются ни одним из трёх правил.
- Правило «некорректный PURL» использует существующую проверку `purl_utils.validate` (`packageurl-python`).
- Удаление выполняется до остальных правил `components.*` и `licenses.*`, чтобы удалённые компоненты не попадали в их статистику и в итоговые `issues`.
- Три новых пункта в карточке «Правки массива components[]» со справкой «(?)» и примерами «До/После».
- Обновлены backend- и frontend-тесты, локализация en/ru и project specs.

### Не-цели

- Приведение PURL к нижнему регистру.
- Удаление компонентов с подкомпонентами, даже если сам компонент не проходит проверку.
- Повторная проверка компонента после удаления его потомков в том же запуске.
- Изменение `metadata.component` и его вложенного дерева — правила работают только с корневым деревом `components[]`.
- Новые endpoint'ы: флаги живут в `ComponentsFixOptions` и сохраняются существующей кнопкой «Сохранить настройки».
- Изменение существующих правил фильтрации, лицензий, необязательных полей и сбора несоответствий.
- Миграция старого `data/sbom_fix_options.json`: отсутствующие поля получают значения по умолчанию через Pydantic.

### Анти-цели

- Удалять контейнер, у которого был непустой `components`, после удаления его потомков.
- Считать отсутствующий или пустой `purl` некорректным в правиле «некорректный PURL» (это зона правила «без PURL»).
- Удалять элементы массива `components`, не являющиеся объектами.
- Удалять ключ `components` целиком, когда массив опустел: остаётся пустой массив `[]`.
- Включать новые правила по умолчанию.
- Считать удалённые компоненты в статистике других правил.
- Дублировать проверку PURL собственным парсером вместо `purl_utils`.

## 3. Ограничения и допущения

- Backend: FastAPI + Pydantic, stdlib; frontend: Vue 3 `<script setup>`, Pinia, vue-i18n.
- Все пользовательские строки — через i18n (`ru`, `en`); ошибки API — машиночитаемые коды.
- Python-код запускается в `.venv`; frontend-проверки — `npm --prefix frontend`.
- `fix_sbom()` не мутирует входной документ (работает на `copy.deepcopy`).
- `purl_utils.validate(purl)` принимает строку и либо возвращает `PurlComponents`, либо возбуждает `PurlValidationError` (обёртка над `ValueError` из `PackageURL.from_string`).
- «Отсутствует» для `purl` и `version` означает: ключа нет, значение `null`, пустая строка или значение не является строкой. Та же трактовка, что у `_is_non_empty_string` в существующем коллекторе.
- «Лист» — компонент, у которого значение `components` отсутствует, равно `null`, не является массивом или является пустым массивом. Непустой массив `components` делает компонент контейнером.
- Листовость фиксируется один раз перед фазой удаления: контейнер, у которого все потомки были удалены этими же правилами, не становится листом и не удаляется в том же запуске.
- Обход дерева — предпорядковый, как у `_walk_components`; `metadata.component` не затрагивается.
- Порядок правил фиксирован; сборка `issues` уже происходит после всех правок (`fixer.py`, конец `fix_sbom`), менять это не нужно.

## 4. Рассмотренные подходы

### Подход A — отдельный рекурсивный фильтр, три последовательных прохода (выбран)

Новая функция вида `_remove_leaf_components(components, leaf_ids, predicate) -> (kept, removed_count)` пересобирает массивы на каждом уровне, удаляя только узлы из заранее вычисленного множества листьев, для которых выполнен предикат. Функция вызывается по одному разу на каждое включённое правило в порядке «без PURL → некорректный PURL → без version» до остальных правил группы.

Плюсы: минимальное вмешательство в существующий код; каждый счётчик и приоритет правил очевидны; легко тестировать; непустые контейнеры защищены явно. Минусы: до трёх обходов дерева (на фоне `deepcopy` и разбора JSON это несущественно).

### Подход B — один обход с объединённым предикатом и счётчиками по правилам

Один проход, в котором для каждого листа последовательно проверяются включённые правила, а счётчик увеличивается у первого сработавшего.

Плюсы: меньше проходов. Минусы: логика приоритетов и подсчёта сложнее, а выигрыш на практике незаметен. Отклонён.

### Подход C — обобщить `_walk_components` до transform-обхода

Переиспользовать существующий helper, научив его возвращать новый список.

Плюсы: нет второй похожей функции обхода. Минусы: меняется общий код, который используют `components.*` и `licenses.*` правила, — лишний риск для уже работающего поведения. Отклонён.

**Решение:** подход A. Листовость вычисляется до первого прохода удаления, чтобы контейнеры не удалялись каскадно.

## 5. Модель опций и API

### 5.1. Backend

```python
class ComponentsFixOptions(BaseModel):
    remove_leaf_missing_purl: bool = False
    remove_leaf_invalid_purl: bool = False
    remove_leaf_missing_version: bool = False
    filter_external_references: bool = True
    filter_properties: bool = True
    fill_missing_gost_properties: bool = False
```

- Новые поля не требуют валидаторов: Pydantic приводит значения к `bool`, неверный тип даёт существующий `400 invalid_options`.
- `_rule_enabled` уже умеет читать id с префиксом `components.` из `options.components`; изменений не требуется.
- `RULE_IDS` становится кортежем из 14 значений. Три правила удаления идут первыми в группе `components` — в том же порядке, в котором выполняются:

```python
RULE_IDS = (
    "reorder",
    "set_spec_version",
    "increment_version",
    "add_timestamp",
    "add_manufacturer",
    "components.remove_leaf_missing_purl",
    "components.remove_leaf_invalid_purl",
    "components.remove_leaf_missing_version",
    "components.filter_external_references",
    "components.filter_properties",
    "components.fill_missing_gost_properties",
    "licenses.filter_non_proprietary",
    "licenses.add_proprietary",
    "licenses.remove_proprietary_source_references",
)
```

- В `_apply_components_rules` сначала выполняются включённые правила удаления, затем существующие фильтрация и заполнение ГОСТ-свойств.

### 5.2. JSON опций

`POST /api/v1/sbom/fix` (поле `options`), `GET/POST /api/v1/sbom/fix/options` и `data/sbom_fix_options.json` получают в блоке `components` три новых ключа:

```json
{
  "components": {
    "remove_leaf_missing_purl": false,
    "remove_leaf_invalid_purl": false,
    "remove_leaf_missing_version": false,
    "filter_external_references": true,
    "filter_properties": true,
    "fill_missing_gost_properties": false
  }
}
```

Старый файл без этих ключей читается без ошибок и получает `false`.

### 5.3. Frontend-типы

В `frontend/src/types/api.ts` интерфейс `ComponentsFixOptions` получает три поля `remove_leaf_missing_purl: boolean`, `remove_leaf_invalid_purl: boolean`, `remove_leaf_missing_version: boolean`. Остальные типы не меняются.

## 6. Правила

Общие положения:

- Обход — корневое дерево `components[]` на любой глубине, предпорядково; `metadata.component` и его поддерево не затрагиваются.
- Перед фазой удаления вычисляется множество идентификаторов листьев: компонент-объект, у которого `components` отсутствует, `null`, не является массивом или является пустым массивом.
- В каждом проходе массивы пересобираются: удаляются только объекты из множества листьев, удовлетворяющие предикату правила. Непустые массивы `components` рекурсивно обрабатываются.
- Если удалены все элементы массива, ключ `components` сохраняется со значением `[]`.
- Элементы массива, не являющиеся объектами, сохраняются как есть (они и сейчас попадают в `component.invalid_entry`).
- Компонент, удалённый более ранним правилом, не участвует в подсчёте последующих правил. Если лист подходит под несколько включённых правил, он учитывается в первом по порядку.
- `count` каждого правила — число удалённых компонентов.

### 6.1. `components.remove_leaf_missing_purl` — «Удалить компоненты-листья без PURL»

Удаляется лист, если `purl` отсутствует, равен `null`, является пустой строкой или значением не-строкового типа.

### 6.2. `components.remove_leaf_invalid_purl` — «Удалить компоненты-листья с некорректным PURL»

Удаляется лист, у которого `purl` — непустая строка и `purl_utils.validate(purl)` возбуждает `PurlValidationError`.

Отсутствующий, `null`, пустой и не-строковый `purl` этим правилом не проверяются и не удаляются: это зона правила 6.1. Если включено только правило 6.2, компонент без `purl` остаётся в документе.

### 6.3. `components.remove_leaf_missing_version` — «Удалить компоненты-листья без version»

Удаляется лист, если `version` отсутствует, равен `null`, является пустой строкой или значением не-строкового типа.

### 6.4. Порядок выполнения и взаимодействие

Внутри `_apply_components_rules`:

1. вычислить множество листьев по исходному (для этой фазы) дереву;
2. при включённом правиле 6.1 — один проход удаления;
3. при включённом правиле 6.2 — один проход удаления;
4. при включённом правиле 6.3 — один проход удаления;
5. существующие правила `components.filter_external_references`, `components.filter_properties`, `components.fill_missing_gost_properties` — по текущему дереву;
6. далее без изменений: `licenses.*`, затем `reorder`, затем сборка `issues`.

Следствия:

- Статистика фильтрации ссылок и свойств, а также добавления ГОСТ-свойств, не учитывает удалённые компоненты.
- `issues` не содержит записей об удалённых компонентах.
- Контейнер, у которого все потомки удалены, остаётся в документе; его собственные `purl`/`version` в этом запуске повторно не проверяются, и он может остаться без `purl`, что отразится в `issues` как `component.missing_purl`.
- `reorder` остаётся последней мутацией; новые правила не меняют порядок ключей.

### 6.5. Статистика

- Три новые строки в порядке `RULE_IDS` — первыми в группе `components`.
- Единица измерения — удалённые компоненты.
- Если правило включено, строка показывается и при нулевом счётчике; выключенные правила в статистику не попадают.
- Подпись строки — существующий `statLabel()` через `t('sbomFixer.rules.' + stat.rule_id)`, поэтому ключи i18n вложены в `rules.components.*`.
- При значениях по умолчанию (все три флага `false`) состав и порядок строк статистики не меняются.

## 7. Интерфейс

Карточка `data-group="components"` получает три новых пункта в начале списка, перед существующими правилами фильтрации. Порядок пунктов совпадает с порядком выполнения и порядком строк статистики.

| # | Rule id | Пункт (ru) | Default |
|---|---|---|---|
| 1 | `components.remove_leaf_missing_purl` | Удалить компоненты-листья без PURL | off |
| 2 | `components.remove_leaf_invalid_purl` | Удалить компоненты-листья с некорректным PURL | off |
| 3 | `components.remove_leaf_missing_version` | Удалить компоненты-листья без version | off |
| 4 | `components.filter_external_references` | Оставить только VCS и source-distribution ссылки | on |
| 5 | `components.filter_properties` | Оставить только ГОСТ-свойства | on |
| 6 | `components.fill_missing_gost_properties` | Добавить недостающие ГОСТ-свойства | off |

- У каждого пункта — `RuleHelp` с описанием и примером «До/После».
- Мастер-чекбокс карточки и кнопки «Выбрать всё» / «Снять всё» учитывают все шесть флагов; расчёт «частично выбрано» не меняется.
- `restoreDefaults()` сбрасывает три новых флага в `false`.
- Отдельных контролов у новых пунктов нет.

## 8. Локализация

`frontend/src/i18n/locales/{ru,en}.json`, пространство `sbomFixer`:

- `rules.components.remove_leaf_missing_purl`, `rules.components.remove_leaf_invalid_purl`, `rules.components.remove_leaf_missing_version` — названия из таблицы 7.1;
- `help.components.remove_leaf_missing_purl`, `help.components.remove_leaf_invalid_purl`, `help.components.remove_leaf_missing_version` — описания: что считается отсутствующим значением, что проверка PURL идёт по спецификации Package URL, что удаляются только компоненты без непустого массива `components`, что опустевший массив остаётся `[]`, что `metadata.component` не затрагивается.

Существующие ключи не переименовываются.

Примеры «До/После» в `sbomFixerRules.ts`:

- без PURL: компонент листа без `purl` исчезает из массива;
- некорректный PURL: лист с `purl: "not-a-purl"` исчезает, лист с корректным PURL остаётся;
- без version: лист без `version` исчезает;
- в примерах полезно показать контейнер с `components`, который остаётся, — по одному такому фрагменту достаточно в справке, не обязательно во всех трёх примерах.

## 9. Тесты

Backend (`tests/test_sbom_fixer.py`, `tests/test_sbom_fix_options_store.py`, `tests/test_sbom_fix_api.py`):

- значения по умолчанию: три флага `false`; `RULE_IDS` содержит 14 id в порядке из 5.1;
- «без PURL»: удаляются листья с отсутствующим, `null`, `""` и не-строковым `purl`; корректный PURL остаётся; удаление работает на всех уровнях вложенности; контейнер с непустым `components` остаётся; пустой массив `components` у листа не мешает удалению; опустевший корневой массив остаётся `[]`; не-объекты сохраняются; счётчик равен числу удалённых;
- «некорректный PURL»: невалидный PURL удаляется, валидный остаётся; отсутствующий/пустой/`null`/не-строковый `purl` не удаляется даже при включённом правиле; `metadata.component.purl` не проверяется; счётчик корректен;
- «без version»: отсутствующий, `null`, `""` и не-строковый `version` удаляются; непустой `version` остаётся; вложенность и листовость работают; счётчик корректен;
- защита контейнеров: контейнер с непустым `components` не удаляется ни одним правилом; контейнер, у которого все потомки удалены другим правилом, сохраняется и не проверяется повторно;
- порядок и приоритет: лист, подходящий под несколько включённых правил, учитывается только в первом; удалённые компоненты не попадают в статистику фильтрации/ГОСТ и в `issues`;
- изоляция: `metadata.component` и его подкомпоненты не затрагиваются;
- API/store: сохранение и загрузка новых флагов, толерантная загрузка старого файла без них, `400 invalid_options` при неверном типе.

Frontend (`frontend/src/views/sbomFixerRules.test.ts`, `frontend/src/views/SbomFixer.test.ts`):

- каталог `COMPONENTS_RULES` содержит 6 правил, всего 14 записей; новые id идут первыми в группе;
- у каждого нового правила есть названия и справка в `ru`/`en`;
- карточка отображает три новых пункта; мастер-чекбокс включает/снимает все шесть флагов; «Выбрать всё» / «Снять всё» работают;
- сохранение настроек и запуск исправления отправляют три новых флага;
- «Сбросить настройки» выставляет три новых флага в `false`.
