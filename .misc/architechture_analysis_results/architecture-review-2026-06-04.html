Architecture Review: Deepening Opportunities

A review of sbom-helper focusing on module depth, testability, and cohesion.

1. Extract SBOM Orchestration from the Router Strong

Files: src/purl_resolver/router.py, src/purl_resolver/sbom/

Problem: The router acts as the domain orchestrator for SBOM enrichment. The resolve_sbom_endpoint manually coordinates JSON parsing, component extraction, deduplication, batch resolution, pre-existing reference storage, and report generation. The HTTP layer is deeply coupled to the internal mechanics of the SBOM workflow.

Solution: Introduce an SbomEnrichmentPipeline module in the Service Layer. The router simply passes the raw file data to the pipeline and returns the result. The pipeline encapsulates the entire lifecycle.

Benefits:

  • Locality: Changes to how SBOMs are enriched happen in one domain service, not in an HTTP handler.
  • Leverage: The router becomes a thin adapter. The complex enrichment logic can be unit-tested without a FastAPI TestClient.

2. Refactor `resolve_purl` into a Pipeline Worth exploring

Files: src/purl_resolver/service.py

Problem: resolve_purl is a "God Function" combining PURL validation, cache lookups, application settings checks, URL validation via HTTP, cache invalidation, and fallback resolver iteration. Furthermore, the router is forced to act as a Service Locator, manually injecting storage, resolvers, and settings_store into every call.

Solution: Create a ResolutionPipeline constructed once at application startup. Use a decorator or middleware pattern (e.g., CacheMiddleware, UrlValidationMiddleware, ProviderMiddleware) to separate concerns. The interface simplifies to pipeline.resolve(purl_str).

Benefits:

  • Locality: URL validation rules and cache logic are isolated from core resolution logic.
  • Leverage: The router doesn't need to know about internal dependencies. Individual pipeline stages can be tested in isolation (e.g., testing URL validation without a real database).

3. Decouple CSV Import from HTTP Layer Worth exploring

Files: src/purl_resolver/router.py, src/purl_resolver/csv_io.py

Problem: In import_csv_endpoint, the router implements the skip_existing strategy by performing N+1 storage.lookup() calls in a loop. Domain logic (deduplication strategy) is handled directly inside the web controller.

Solution: Create a CsvImportService that accepts raw CSV text and an ImportStrategy. Move the loop and deduplication logic into the service (or better, use a bulk database query to identify existing rows).

Benefits:

  • Locality: Import strategies are defined in the domain layer, making it trivial to add a CLI interface later.
  • Leverage: The router becomes purely responsible for file uploads and HTTP responses.

Top Recommendation

Extract SBOM Orchestration from the Router (Candidate 1) is the most critical deepening opportunity. The HTTP handler is currently acting as a complex workflow orchestrator. By creating an SbomEnrichmentPipeline, we immediately improve testability, decouple the domain from FastAPI, and clarify the responsibilities of the Service Layer.
