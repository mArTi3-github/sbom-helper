## Context

Текущий MVP сохраняет результаты резолвинга только в файловом кэше purl2repo, который кэширует HTTP-ответы registry API, а не конечные результаты PURL→repository_url. При повторном запросе того же PURL purl2repo вызывается заново. Для Phase 2 требуется персистентное хранилище с проверкой перед вызовом резолвера.

Констрейнты из архитектуры: API Layer не должен знать о деталях storage; модуль `storage/` должен быть resolver-agnostic для будущего multi-resolver.

## Goals / Non-Goals

**Goals:**
- Сохранять успешные результаты резолвинга в PostgreSQL
- При повторном запросе того же PURL возвращать результат из БД без вызова резолвера
- Graceful degradation при отказе БД
- Расширяемая архитектура для multi-resolver в будущем

**Non-Goals:**
- Хранение неуспешных результатов (repository_url = null)
- Redis
- Миграции через Alembic
- Batch-резолвинг и SBOM enrichment (отложены на будущее)

## Decisions

1. **PostgreSQL, не Redis**: данные должны переживать рестарт контейнера. Redis с persistence — дополнительная сложность без выгоды для одной таблицы.
2. **asyncpg, не SQLAlchemy**: два запроса (SELECT, INSERT) не оправдывают ORM. При расширении схемы рефакторинг на SQLAlchemy тривиален — меняется только `storage/postgres.py`.
3. **Храним только успешные результаты**: неуспешные не кэшируем — это позволяет повторно разрешать PURL, которые могли стать резолвимыми. Также избегаем проблем с TTL для «вечных нулей».
4. **Отдельный StorageSettings с префиксом DB_**: инфраструктурные настройки не смешиваются с настройками резолверов (`PURL2REPO_*`), что важно при добавлении LLM-резолвера и других.
5. **Graceful degradation**: try/except вокруг вызовов БД. При ошибке `lookup()` → логируем, вызываем резолвер. При ошибке `store()` → логируем, возвращаем результат без сохранения.
6. **File-based cache purl2repo остаётся**: кэширует HTTP-ответы registry API — другой уровень, не конфликтует с БД.

## Risks / Trade-offs

- **[Данные устаревают]** Результат резолвинга может измениться (пакет сменил репозиторий). Сейчас механизма инвалидации нет. → Принимается для MVP Phase 2; механизм рефреша можно добавить позже (TTL колонка, фоновый рефреш).
- **[Отказ БД]** Если PostgreSQL недоступен, сервис работает без кэширования. → Graceful degradation, ошибки в логах.
- **[Отсутствие миграций]** `CREATE TABLE IF NOT EXISTS` не поддерживает ALTER TABLE. → Для одной таблицы достаточно. Alembic — при появлении сложных изменений схемы.
