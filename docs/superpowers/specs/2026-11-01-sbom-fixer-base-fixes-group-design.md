# «Исправить SBOM» — подраздел «Базовые правки» и полное отображение несоответствий: дизайн

Документ дополняет и частично заменяет `2026-10-26-sbom-fixer-design.md`, `2026-10-29-sbom-fixer-optional-fields-design.md` и `2026-10-29-sbom-fixer-rule-help-design.md` в части состава статических правил, структуры опций и группировки пунктов в интерфейсе. При расхождениях приоритет у этого документа.

## 1. Задача и зачем

Сейчас страница `/fix-sbom` делит статические правила по объектам SBOM: отдельные карточки «Корневой объект», «metadata» (с вложенным блоком «metadata.component») и «components». Три из них содержат по одному правилу упорядочивания (`root.reorder`, `metadata.reorder`, `metadata_component.reorder`, `components.reorder` — четыре флага), хотя для пользователя это одна операция «привести поля в нужный порядок». Группировка по объектам заставляет читать четыре карточки, чтобы включить одно действие, и не отражает то, как пользователь думает о правках.

Кроме того, таблица «Показать несоответствия» обрезает значения: ячейки принудительно однострочные, с фиксированной раскладкой и `text-overflow: ellipsis`, поэтому «Отсутствует ссылка на исхо…» и `$.components[0].componen…` не читаются. Полный текст виден только во всплывающей подсказке.

Нужно:

- объединить четыре правила упорядочивания в одно правило «Упорядочить поля»;
- заменить группировку по объектам на три подраздела: **«Базовые правки»**, **«Правки массива components[]»**, **«Удаление необязательных полей по „белому списку“»**;
- показывать содержимое таблицы несоответствий полностью.

## 2. Цели, не-цели и анти-цели

### Цели

- Один подраздел «Базовые правки» содержит все правила, которые раньше были в «Корневом объекте», «metadata» и «metadata.component», плюс объединённое «Упорядочить поля».
- Названия базовых пунктов содержат точный путь поля, так как рядом больше нет карточки, которая задавала бы объект.
- Одно правило `reorder` вместо четырёх: один флаг в опциях, один rule id, одна строка статистики.
- Модель опций приводится в соответствие интерфейсу: «базовые» флаги становятся плоскими полями `SbomFixOptions`, вложенными остаются только `components` и `optional_fields`.
- Подраздел «Правки массива components[]» содержит три оставшихся правила компонентов; подраздел белого списка не меняется.
- Таблица несоответствий показывает значения целиком, с переносом строк и без горизонтальной прокрутки.
- Обновлены project specs, локализация en/ru, backend- и frontend-тесты.

### Не-цели

- Изменение набора кодов несоответствий и логики их сбора.
- Изменение анализа необязательных полей, белых списков и их API.
- Изменение порядка выполнения правил, кроме объединения упорядочивания.
- Поддержка обратной совместимости с прежней формой опций, прежними rule id и прежним `data/sbom_fix_options.json` — миграции нет.
- Новые правила, новые проверки, новые endpoint'ы.
- Переработка остальных таблиц страницы (кандидаты на удаление, справочник ФСТЭК, статистика) кроме тех изменений, которые следуют из новой модели.

### Анти-цели

- Оставить старые вложенные модели `root`/`metadata`/`metadata.component` или старые флаги `*.reorder` «на всякий случай».
- Показать базовые пункты одновременно в новой карточке и в старых карточках.
- Показывать в статистике четыре строки упорядочивания.
- Сохранить обрезание строк или заменить его горизонтальной прокруткой таблицы несоответствий.
- Изменить поведение правила упорядочивания (порядок ключей, охват объектов).
- Добавить повторный проход по документу или лишнюю копию: раздел должен по-прежнему работать с файлами 100+ МБ.

## 3. Ограничения и допущения

- Обратная совместимость не требуется; реализация делается в чистом виде, без миграций и совместимых веток кода.
- Backend: FastAPI + Pydantic, stdlib; frontend: Vue 3 `<script setup>`, Pinia, vue-i18n.
- Все пользовательские строки — через i18n (`ru`, `en`); ошибки API — машиночитаемые коды.
- Python-код запускается в `.venv`; frontend-проверки — `npm --prefix frontend`.
- `dict` в Python сохраняет порядок вставки; правило упорядочивания переставляет ключи, не меняя значения.
- Входной документ не мутируется: `fix_sbom()` работает на `copy.deepcopy`.
- Правило упорядочивания остаётся последней мутацией документа.
- Старый файл опций читается толерантно: неизвестные ключи игнорируются, отсутствующие поля берут значения по умолчанию.

## 4. Рассмотренные подходы

### Подход 1 — плоские «базовые правки» (выбран)

Верхний уровень `SbomFixOptions` становится зеркалом интерфейса: `reorder`, `set_spec_version`, `spec_version`, `increment_version`, `add_timestamp`, `add_manufacturer`, `manufacturer`; рядом — вложенные `components` (три правила) и `optional_fields`. Вложенные `root`, `metadata`, `metadata.component` удаляются.

Плюсы: модель, контракт, файл настроек и интерфейс говорят на одном языке; `_rule_enabled` перестаёт разбирать префиксы (кроме `components.`); фронтенд читает базовые флаги по одному пути. Минусы: шире diff — меняются модель, контракт опций, тесты и specs.

### Подход 2 — слить только `reorder`

Добавить верхнеуровневый `reorder`, а `root`/`metadata`/`metadata.component` оставить без поля `reorder`.

Плюсы: меньше diff. Минусы: три вложенных объекта остаются в API и в файле настроек, хотя в интерфейсе им больше ничто не соответствует; фронтенд продолжает читать флаги по трём разным путям, `_rule_enabled` — разбирать префиксы. Это ровно та вложенность, которую нужно убрать. Отклонён.

### Подход 3 — плоская модель целиком

Сделать плоскими и правила `components`. Отклонён: подраздел «Правки массива components[]» остаётся, поэтому вложенность `components` по-прежнему осмысленна и соответствует карточке интерфейса.

**Решение:** подход 1.

## 5. Итоговая структура страницы

Три подраздела, каждый — карточка с мастер-чекбоксом и кнопками «Выбрать всё» / «Снять всё» (у карточки белого списка — своя шапка с кнопкой «Проанализировать», как сейчас).

### 5.1. «Базовые правки» (`data-group="basic"`)

Порядок пунктов:

| # | Rule id | Пункт (ru) | Пункт (en) | Дополнительный контрол |
|---|---|---|---|---|
| 1 | `reorder` | Упорядочить поля | Reorder fields | — |
| 2 | `set_spec_version` | Установить $.specVersion | Set $.specVersion | текстовое поле «Версия спецификации», активно только при включённом пункте |
| 3 | `increment_version` | Увеличить $.version | Increment $.version | — |
| 4 | `add_timestamp` | Добавить $.metadata.timestamp, если отсутствует | Add $.metadata.timestamp if missing | — |
| 5 | `add_manufacturer` | Добавить $.metadata.component.manufacturer, если отсутствует | Add $.metadata.component.manufacturer if missing | текстовое поле «Производитель», активно только при включённом пункте |

Мастер-чекбокс управляет пятью булевыми флагами и не трогает текстовые значения. Состояние «частично выбрано» вычисляется по тем же пяти флагам.

**Правило наименования.** Путь указывается в названии, только если по заголовку карточки нельзя однозначно определить объект. В «Базовых правках» собраны правила четырёх разных объектов, поэтому путь обязателен для правил, нацеленных на один путь. Исключение — объединённый `reorder`: он затрагивает несколько объектов, поэтому название остаётся кратким («Упорядочить поля»), а полный перечень объектов и порядок ключей описаны в справке по кнопке «i». В карточке «Правки массива components[]» заголовок уже задаёт массив, поэтому названия трёх правил остаются краткими и путь в них не дублируется.

### 5.2. «Правки массива components[]» (`data-group="components"`)

| # | Rule id | Пункт |
|---|---|---|
| 1 | `components.filter_external_references` | Оставить только VCS и source-distribution ссылки |
| 2 | `components.filter_properties` | Оставить только GOST-свойства |
| 3 | `components.fill_missing_gost_properties` | Добавить недостающие ГОСТ-свойства |

Правила `components.reorder` здесь больше нет — оно вошло в объединённое «Упорядочить поля».

### 5.3. «Удаление необязательных полей по „белому списку“»

Без изменений: кнопка анализа, таблица кандидатов, справочник ФСТЭК, редактируемый список «не рекомендуется удалять».

### 5.4. Результаты

«Статистика изменений» и «Показать несоответствия» остаются отдельными блоками после запуска исправления.

## 6. Модель опций и API

### 6.1. Backend

```python
class ComponentsFixOptions(BaseModel):
    filter_external_references: bool = True
    filter_properties: bool = True
    fill_missing_gost_properties: bool = False

class OptionalFieldsFixOptions(BaseModel):
    keep: list[str] = Field(default_factory=lambda: list(DEFAULT_KEEP_FIELDS))

class SbomFixOptions(BaseModel):
    reorder: bool = True
    set_spec_version: bool = True
    spec_version: str = "1.7"                 # валидатор ^\d+\.\d+$, trim
    increment_version: bool = True
    add_timestamp: bool = True
    add_manufacturer: bool = True
    manufacturer: str = "Positive Technologies"  # валидатор: trim, непустая строка
    components: ComponentsFixOptions = Field(default_factory=ComponentsFixOptions)
    optional_fields: OptionalFieldsFixOptions = Field(default_factory=OptionalFieldsFixOptions)
```

- Валидаторы `spec_version` и `manufacturer` переносятся на `SbomFixOptions` без изменения правил.
- `_rule_enabled` упрощается: для id с префиксом `components.` — `getattr(options.components, ...)`, иначе `getattr(options, rule_id)`.
- `RULE_IDS` становится кортежем из 8 значений в порядке статистики:

```python
RULE_IDS = (
    "reorder",
    "set_spec_version",
    "increment_version",
    "add_timestamp",
    "add_manufacturer",
    "components.filter_external_references",
    "components.filter_properties",
    "components.fill_missing_gost_properties",
)
```

- Функции `_apply_root_rules`, `_apply_metadata_rules`, `_apply_reorders` сохраняют ответственность за свои объекты, но читают плоские поля опций; `_apply_reorders` заменяется на `_apply_reorder`.
- Порядок выполнения `fix_sbom()` не меняется: удаление необязательных полей → `specVersion`/`version` → `timestamp`/`manufacturer` → фильтры компонентов → упорядочивание последним.

### 6.2. JSON опций

`POST /api/v1/sbom/fix` (поле `options`), `GET/POST /api/v1/sbom/fix/options` используют новую форму:

```json
{
  "reorder": true,
  "set_spec_version": true,
  "spec_version": "1.7",
  "increment_version": true,
  "add_timestamp": true,
  "add_manufacturer": true,
  "manufacturer": "Positive Technologies",
  "components": {
    "filter_external_references": true,
    "filter_properties": true,
    "fill_missing_gost_properties": false
  },
  "optional_fields": { "keep": ["..."] }
}
```

Старые ключи `root`, `metadata`, `components.reorder` в существующем файле настроек игнорируются (Pydantic отбрасывает неизвестные поля), недостающие значения берутся по умолчанию; отдельного кода миграции нет.

### 6.3. Frontend-типы

В `frontend/src/types/api.ts`:

- удаляются `RootFixOptions`, `MetadataFixOptions`, `MetadataComponentFixOptions`;
- `ComponentsFixOptions` теряет `reorder`;
- `SbomFixOptions` получает плоские поля из 6.1.

`SbomFixStat` и `SbomFixIssue` не меняются.

## 7. Правило `reorder`

- Включается одним флагом `options.reorder`.
- Если включено, последовательно упорядочиваются: корневой объект (`ROOT_PRIORITY`), `metadata` (`METADATA_PRIORITY`), `metadata.component` (`METADATA_COMPONENT_PRIORITY`), затем каждый компонент дерева `components[]` рекурсивно (`COMPONENT_PRIORITY`).
- Охват и порядок ключей не меняются по сравнению с прежними четырьмя правилами; `metadata.component.components` по-прежнему не обходится.
- Не-объектные узлы пропускаются без ошибок, как сейчас.
- Если флаг выключен, упорядочивание не выполняется, правило отсутствует в статистике.

## 8. Статистика

- Строка `reorder` одна. `count` — число объектов, у которых изменился порядок ключей: корень, `metadata`, `metadata.component` и каждый компонент дерева `components[]` дают по 1. Так единица измерения однородна («сколько объектов упорядочено»), в отличие от прежнего смешения «1 за объект» и «N за компоненты».
- Порядок строк статистики — порядок `RULE_IDS`; строки удаления необязательных полей идут после, как сейчас.
- По умолчанию в статистике 7 статических строк (8 правил минус выключенный `components.fill_missing_gost_properties`).
- Подпись строки — `sbomFixer.rules.reorder` («Упорядочить поля»); `statLabel()` продолжает работать через `t('sbomFixer.rules.' + stat.rule_id)`.

## 9. Отображение несоответствий

Проблема в CSS таблицы `issues-table`: `table-layout: fixed`, фиксированные проценты ширины колонок и `overflow: hidden; text-overflow: ellipsis; white-space: nowrap` на ячейках.

Изменения:

- убрать `table-layout: fixed`, фиксированные ширины `.issue-code`, `.issue-path`, `.issue-component`, `.issue-details` и правила обрезания;
- разрешить перенос: `white-space: normal` (по умолчанию) и `overflow-wrap: anywhere` для ячеек с путями, кодами, именами компонентов и JSON-деталями, чтобы длинные неразрывные строки не выходили за карточку;
- обёртку оставить с вертикальной прокруткой и `max-height`, горизонтальную прокрутку не добавлять (`overflow-y: auto; overflow-x: hidden`);
- убрать `:title` у ячеек таблицы несоответствий: полный текст теперь виден и подсказка не нужна.

Ожидаемый результат: значения показываются целиком, строки при необходимости становятся выше; при очень длинных деталях таблица остаётся в пределах карточки.

## 10. Локализация

`frontend/src/i18n/locales/{ru,en}.json`, пространство `sbomFixer`:

- `groups`: остаются `basic` («Базовые правки» / «Basic fixes») и `components` («Правки массива components[]» / «components[] edits»); `root`, `metadata`, `metadataComponent` удаляются;
- `rules`: базовые правила становятся плоскими ключами `reorder`, `set_spec_version`, `increment_version`, `add_timestamp`, `add_manufacturer`; значения этих ключей — названия с путями из таблицы 5.1; `rules.components` сохраняет три ключа без `reorder` (названия без путей);
- `help`: аналогично — плоские ключи для базовых правил и три ключа для компонентов; текст `help.reorder` описывает упорядочивание корня, `metadata`, `metadata.component` и компонентов; пример «До/После» — один компактный фрагмент, показывающий все четыре уровня;
- подписи `specVersion`, `manufacturer`, `selectAll`, `clearAll` не меняются; `optionalFields.*` не меняется.

## 12. Что остаётся на усмотрение исполнителя

- Точные CSS-значения для переноса строк и ширины колонок таблицы несоответствий; критерий — текст виден целиком, горизонтальной прокрутки нет, карточка не расширяется.
- Формулировки текста помощи и содержимое объединённого примера «До/После» для `reorder` при сохранении смысла, описанного в разделе 7.
- Разбиение тестов на файлы и набор конкретных проверок внутри описанных требований.
- Порядок внутренних функций в `fixer.py`, если он не меняет порядок выполнения правил и статистику.
