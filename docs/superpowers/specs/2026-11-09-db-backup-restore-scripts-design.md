# Дизайн: скрипты полного бэкапа и восстановления БД

Дата: 2026-11-09
Статус: на утверждении

## 1. Зачем

Нужен перенос накопленных сопоставлений `PURL → Repository URL` между
стендами sbom-helper, а также резервная копия на случай потери данных.
Сейчас в разделе «Управлять БД» экспорт работает только для выделенных
строк: `POST /api/v1/db/export` получает список PURL и делает отдельный
`lookup` на каждый. Для основного стенда с 5+ млн строк это неприменимо.

Бэкап и восстановление должны выполняться на хосте стенда через консоль:
доступ по SSH есть, Docker Compose используется, PostgreSQL привязан к
проекту. Веб-интерфейс остаётся вспомогательным: в нём нужны только
краткие справочные инструкции.

## 2. Цели

- `scripts/db_backup.sh` — выгружает всё содержимое таблицы `resolved_purls`
  в один сжатый файл.
- `scripts/db_restore.sh` — восстанавливает файл на целевом стенде.
- Сохраняются все четыре столбца: `purl`, `repository_url`, `resolver`,
  `resolved_at`.
- По умолчанию восстановление работает в режиме `merge`: существующие на
  стенде строки не изменяются, добавляются только отсутствующие `purl`.
- Режим `replace` полностью заменяет содержимое таблицы данными из файла.
- В логах скриптов явно видны режим, файл и итоговые счётчики строк.
- В «Управлять БД» и `README.md` появляются краткие инструкции со ссылками
  на скрипты.

## 3. Не-цели

- Не добавляем загрузку/восстановление бэкапа через веб-интерфейс.
- Не бэкапим таблицу `jobs`, настройки приложения, ignore-паттерны и кэш
  валидации URL: это служебные/производные данные. Настройки и паттерны
  лежат файлами в `data/` и при необходимости копируются отдельно.
- Не делаем автоматическое расписание, ротацию по расписанию и загрузку
  файла на удалённое хранилище. Допускается только необязательный флаг
  `--keep N` для локальной ротации.
- Не меняем существующий API и текущий экспорт выделенных строк.

## 4. Рассмотренные подходы

### 4.1. Формат файла

1. **`pg_dump -Fc` (custom).** Стандартный формат, сохраняет схему, есть
   `pg_restore -l`, `--single-transaction`. Но для слияния в непустую БД
   `pg_restore --data-only` падает на конфликтах первичного ключа; нужен
   временный database и дополнительная переливка. Файл непрозрачный,
   привязан к мажорной версии PostgreSQL. Схема и так управляется
   приложением через `storage/schema.sql`, поэтому её сохранение не нужно.
2. **Plain SQL (`INSERT`/`COPY`-дамп).** Читаемый, но для 5 млн строк
   получается очень большой и медленный; слияние всё равно требует
   ручного SQL.
3. **CSV (RFC 4180) + gzip, загрузка через `COPY` (выбран).** Данные
   простых типов (`TEXT`, `TIMESTAMPTZ`, `NOT NULL`) переносятся без
   потерь. Один файл ~1 ГБ без сжатия и ~200–300 МБ в gzip. Одинаково
   хорошо поддерживает и `merge`, и `replace`; переносим между версиями
   PostgreSQL; файл можно проверить глазами.

### 4.2. Путь восстановления

1. **Только через веб-интерфейс.** Удобнее для не-администраторов, но
   требует потоковой загрузки ~1 ГБ через браузер, нового upload-эндпоинта
   и фоновой задачи импорта.
2. **Только консольные скрипты (выбран).** Администратор выполняет одну
   команду на сервере; нет загрузки большого файла через браузер, нет
   нового API, восстановление не зависит от работающего приложения.
3. **Оба пути.** Больше кода и тестов; отложено до появления реальной
   потребности у не-администраторов. Формат CSV.gz совместим с будущим
   UI-импортом без переделки экспорта.

### 4.3. Поведение merge при совпадении `purl`

1. **Побеждает запись из бэкапа.** Просто, но импорт старой копии затрёт
   более свежие данные стенда.
2. **Побеждает существующая строка стенда (выбран).** Импортируются только
   отсутствующие `purl`; существующие строки не перезаписываются, поэтому
   merge дешевле (нет новых версий строк и лишнего WAL) и безопаснее.
   Устаревшие записи стенда merge не обновляет — для полного обновления
   есть `--replace`.
3. **Побеждает более свежий `resolved_at`.** Сложнее семантика; сравнение
   выполняется в `ON CONFLICT`, но всё равно перезаписывает часть строк.

## 5. Дизайн

### 5.1. Контракт файла

- Имя по умолчанию:
  `backups/sbom_purls_YYYYMMDD-HHMMSS.csv.gz` (время UTC).
- UTF-8, разделитель — запятая, заголовок первой строкой.
- Колонки строго в порядке:
  `purl,repository_url,resolver,resolved_at`.
- Экспорт выполняется с `PGTZ=UTC`, чтобы `resolved_at` не зависел от
  таймзоны стенда.
- Строки упорядочены по `purl` (детерминированный файл, используется
  первичный ключ).
- Каталог `backups/` добавляется в `.gitignore`; файлы создаются с
  ограничением доступа (`umask 077`).
- Перед загрузкой проверяется первая строка файла: она должна точно
  совпадать с заголовком `purl,repository_url,resolver,resolved_at`.
  Файл с другим порядком колонок или без заголовка отклоняется, чтобы не
  загрузить данные в перепутанные поля.

### 5.2. `scripts/db_backup.sh`

Запускается на хосте из любого каталога, сам переходит в корень репозитория
(как `scripts/update.sh`). Использует `docker compose -f docker-compose.yml
exec -T db psql`, то есть не требует установленного локально PostgreSQL-
клиента и не зависит от образа приложения.

Псевдокод:

```bash
docker compose exec -T -e PGTZ=UTC db \
  psql -U "$DB_USER" -d "$DB_NAME" -v ON_ERROR_STOP=1 \
  -c "COPY (SELECT purl, repository_url, resolver, resolved_at
             FROM resolved_purls ORDER BY purl)
      TO STDOUT WITH (FORMAT csv, HEADER true)" \
  | gzip > "$OUTFILE"
```

Флаги:

- `-o FILE` / `--output FILE` — путь к файлу (по умолчанию см. выше).
- `--keep N` — после успешной выгрузки удалить старые файлы
  `sbom_purls_*.csv.gz`, оставив `N` последних (необязательно).
- `-v` — подробный вывод (в стиле `update.sh`).

После выгрузки скрипт печатает путь, размер, количество строк в файле
(без заголовка) и завершается с ненулевым кодом при любой ошибке
(`set -euo pipefail`, `ON_ERROR_STOP=1`).

### 5.3. `scripts/db_restore.sh`

Синтаксис:

```bash
./scripts/db_restore.sh FILE [--mode merge|replace] [--yes]
```

- `--mode merge` — режим по умолчанию.
- `--mode replace` — требует подтверждения в интерактивном терминале или
  флага `--yes`; иначе скрипт завершается с ошибкой.
- `--yes` — не задавать вопросов (для неинтерактивного запуска).

**merge (по умолчанию):**

1. Проверить заголовок файла (см. контракт выше).
2. Создать временную staging-таблицу
   `resolved_purls_import_<pid> (LIKE resolved_purls INCLUDING DEFAULTS)` и
   очистить её. PID в имени исключает столкновение двух одновременных
   восстановлений.
3. Потоково загрузить файл в staging через
   `\copy resolved_purls_import_<pid> (purl, repository_url, resolver, resolved_at)
   FROM STDIN WITH (FORMAT csv, HEADER true)`.
4. Перенести данные в `resolved_purls`:
   ```sql
   INSERT INTO resolved_purls (purl, repository_url, resolver, resolved_at)
   SELECT purl, repository_url, resolver, resolved_at
   FROM resolved_purls_import_<pid>
   ON CONFLICT (purl) DO NOTHING;
   ```
5. Посчитать и вывести: `inserted` (сколько добавлено), `skipped`
   (сколько уже было на стенде или продублировано в файле), `total`
   (строк в файле).
6. Удалить staging-таблицу (в том числе при ошибке — через trap).

Существующие строки не изменяются. Строки, которых нет в файле, остаются.

**replace:**

1. Запросить подтверждение, если не передан `--yes`.
2. Проверить заголовок и загрузить файл в staging-таблицу так же, как в
   merge.
3. Если в staging нет строк — отказаться от замены, чтобы не очистить
   таблицу пустым/битым файлом.
4. В одной транзакции выполнить `TRUNCATE resolved_purls` и
   `INSERT ... SELECT DISTINCT ON (purl) ... ORDER BY purl, resolved_at DESC`.
   При дубликатах `purl` внутри файла остаётся запись с самым свежим
   `resolved_at`. Транзакция гарантирует, что при ошибке таблица не
   останется пустой.
5. Вывести `inserted` и `total`.

Предупреждение в логах: `replace` удаляет строки, которых нет в файле, и
на время транзакции берёт блокировку на таблицу.

**Общее:**

- `set -euo pipefail`; при ошибке — ненулевой код возврата и понятное
  сообщение.
- Проверяется, что сервис `db` запущен.
- В логах первой строкой: `[restore <ts>] mode: merge` (или `replace`),
  путь к файлу, целевые `DB_USER`/`DB_NAME`.
- Параметры `DB_USER` и `DB_NAME` можно переопределить переменными
  окружения; по умолчанию `sbom`/`sbom`.
- Проверяется, что `gzip` доступен на хосте.

### 5.4. UI: раздел «Управлять БД»

Добавляется свёрнутый блок «Резервное копирование БД» (компонент
`frontend/src/components/db/DbBackupHelp.vue`, подключается в
`DatabaseAdmin.vue` рядом с `DbImportModal`). Содержимое — краткая
справка:

- полный бэкап и перенос выполняются скриптами на сервере;
- `./scripts/db_backup.sh` — создать файл в `backups/`;
- `./scripts/db_restore.sh backups/<file>.csv.gz` — восстановить (по
  умолчанию merge: добавляются только отсутствующие PURL);
- `--mode replace` — полная замена таблицы;
- текущий экспорт выделенных строк остаётся отдельной функцией.

Строки добавляются в `ru.json` и `en.json` (`dbAdmin.backupHelp.*`).

## 6. Проверка

- `bash -n scripts/db_backup.sh scripts/db_restore.sh`.
- Ручной сценарий на локальном `docker compose`:
  1. наполнить `resolved_purls` небольшим набором;
  2. сделать бэкап, проверить заголовок и число строк;
  3. добавить/изменить строки на «целевом» стенде и выполнить merge:
     существующие строки не меняются, отсутствующие добавляются;
  4. выполнить `--mode replace` и убедиться, что таблица совпадает с файлом;
  5. проверить, что при ошибке (битый файл, недоступная БД) скрипт
     завершается с ненулевым кодом и не оставляет staging-таблицу.
- Frontend: `npm --prefix frontend run test` (проверка отображения справки
  в `DatabaseAdmin.test.ts`).
- Backend-тесты не затрагиваются, но перед завершением запускается полный
  `pytest` согласно `AGENTS.md`.

## 7. Что оставляем исполнителю

- Точные тексты справки и место блока в вёрстке.
- Формат логов и набор выводимых счётчиков (в пределах описанного).
- Необязательный `--keep N` и значение по умолчанию, если флаг не задан.
- Небольшие детали реализации staging-таблицы и подсчёта `inserted`.
