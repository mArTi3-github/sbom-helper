# Дизайн: правило `components.add_provided_by` в разделе «Исправить SBOM»

Дата: 2026-11-02
Статус: на согласовании

## 1. Зачем

Методика ФСТЭК допускает не указывать `externalReferences` с `vcs` или
`source-distribution`, если программный компонент заимствован из
сертифицированного СЗИ, входящего в среду функционирования ОО, и в
`properties[]` указано свойство `GOST:provided_by` с названием этого СЗИ
(`.misc/addictional_materials/sbom_description_fstec.md`, таблица П.5,
исключение 2). Сейчас в разделе «Исправить SBOM» такое свойство можно только
проставить вручную или внешним скриптом
(`.misc/addictional_materials/add_astra_gostfields.py`).

Нужен штатный пункт в группе «Правки массива components[]», который по
настраиваемому набору признаков компонента добавляет `GOST:provided_by` и тем
самым снимает для него требование ссылки на исходные тексты в том же прогоне
исправления.

## 2. Цели и не-цели

Цели:

- Новый пункт «Добавить свойство GOST:provided_by для компонентов со
  следующими признаками:» в группе `components[]`.
- Пункт включён по умолчанию.
- Построчный редактор из трёх столбцов: «Поле», «Значение», «Название
  сертифицированного СЗИ».
- Для подходящего компонента в `properties[]` добавляется
  `{"name": "GOST:provided_by", "value": "<название СЗИ из строки>"}`.
- Стартовая строка по умолчанию: `purl` / `pkg:deb/astra` /
  `Операционная система специального назначения "Astra Linux Special Edition"`.
- Правило учитывается в статистике и в проверке несоответствий: компонент,
  получивший свойство в этом же прогоне, не должен попадать в
  `component.missing_source_reference`.

Не-цели:

- Не проверяем сертификат, состав среды функционирования и классы
  `attack_surface`/`security_function` СЗИ — это ответственность пользователя,
  который заполняет строки.
- Не меняем правило `components.fill_missing_gost_properties`.
- Не трогаем `metadata.component` и его поддерево (как и все `components.*`
  правила).
- Не добавляем другие свойства `GOST:*` по шаблонам.
- Не выносим общий компонент редактора строк: редактор нового правила
  реализуется локально в `SbomFixer.vue` (решение согласовано).

## 3. Рассмотренные подходы

1. **Зеркально `licenses.add_proprietary` (выбран).** Плоские поля в
   `ComponentsFixOptions`: булев `add_provided_by` и список
   `provided_by_patterns` из объектов `{field, pattern, provided_by}`.
   Совпадает с уже принятой моделью опций, `_rule_enabled` и generic-рендер
   правил работают без спецкейсов. Минус: в `components` появляется небулев
   ключ, как `add_patterns` в `licenses`.
2. **Вложенный блок `components.provided_by: {enabled, patterns}`.** Доменно
   аккуратнее, но ломает `_rule_enabled` и цикл
   `options.components[rule.key]` во фронтенде; нужны спецкейсы без выигрыша
   для пользователя.
3. **Отдельная группа «GOST-свойства».** Противоречит требованию положить
   пункт в `components[]` и разрывает родственные правила.

## 4. Поведение правила

### 4.1. Модель опций

```python
class ProvidedByPatternItem(BaseModel):
    field: str = ""
    pattern: str = ""
    provided_by: str = ""


class ComponentsFixOptions(BaseModel):
    ...
    add_provided_by: bool = True
    provided_by_patterns: list[ProvidedByPatternItem] = Field(
        default_factory=lambda: [
            ProvidedByPatternItem(
                field="purl",
                pattern="pkg:deb/astra",
                provided_by=(
                    'Операционная система специального назначения '
                    '"Astra Linux Special Edition"'
                ),
            )
        ]
    )
```

`components.add_provided_by` добавляется в `RULE_IDS` сразу после
`components.fill_missing_gost_properties` и перед `licenses.*`. Порядок в
`RULE_IDS` задаёт порядок строк статистики и порядок правил в UI-каталоге.

### 4.2. Матчинг строк

- Активная строка — та, у которой после обрезки пробелов непусты все три
  значения: `field`, `pattern`, `provided_by`. Строки с пустым любым из трёх
  полей игнорируются (аналог пустых `field`/`pattern` у Proprietary).
- Поле ищется только на верхнем уровне объекта компонента
  (`component.get(field)`); вложенные объекты и массивы как поля не
  разыменовываются.
- Поле отсутствует или равно `null` — строка не совпадает. Иначе совпадение,
  если `pattern` является подстрокой `str(value)` с учётом регистра. Это
  ровно семантика `licenses.add_proprietary`, поэтому `_matches_license_patterns`
  обобщается в небольшой helper, а не дублируется.
- Строки просматриваются сверху вниз. Первая активная совпавшая строка задаёт
  `provided_by`; остальные строки для этого компонента не рассматриваются.
- Обход — всё дерево корневого `components[]` (каждый корневой компонент и его
  вложенные `components`, pre-order). `metadata.component` и его поддерево не
  обходятся.

### 4.3. Условие обработки компонента

Компонент обрабатывается, только если у него:

- нет ни одного элемента `properties[]` с `name == "GOST:provided_by"`, или
- все такие элементы имеют «пустое» значение.

«Заполненным» считается значение, которое является строкой и после обрезки
пробелов непусто. Всё остальное считается пустым: отсутствие `value`, `null`,
`""`, строка из пробелов, число, объект, массив. Если найден хотя бы один
заполненный `GOST:provided_by`, компонент исключается из обработки целиком —
существующее значение не перезаписывается.

Если заполненного свойства нет, но элемент с таким именем уже существует,
значение записывается в первый такой элемент (позиция в массиве сохраняется),
дубликаты не создаются. Если элемента нет, он добавляется в конец
`properties[]`.

Если `properties` отсутствует или `null` — создаётся массив. Если `properties`
присутствует и не является массивом — компонент пропускается без перезаписи
(как в `components.fill_missing_gost_properties`).

### 4.4. Место в конвейере

Порядок внутри `_apply_components_rules` для каждого компонента:

1. `components.filter_external_references`;
2. `components.filter_properties`;
3. `components.fill_missing_gost_properties`;
4. `components.add_provided_by`.

Правило добавлено после `fill_missing_gost_properties`, чтобы в только что
созданный массив `properties[]` можно было писать. `filter_properties`
оставляет свойства с префиксом `GOST:`, поэтому добавленное свойство не будет
удалено независимо от порядка. Удаление листьев (`components.remove_leaf_*`)
по-прежнему выполняется отдельным проходом до этого блока.

`fix_sbom()` вызывает `_apply_components_rules` до `_apply_licenses_rules` и до
сбора issues, поэтому:

- `component.missing_source_reference` для компонента, получившего свойство в
  этом прогоне, не выставляется;
- если компонент одновременно получает `Proprietary` по правилу лицензий,
  правило `licenses.remove_proprietary_source_references` всё равно удалит у
  него `vcs`/`source-distribution` — это осознанное поведение каждого правила
  в своей области, а не конфликт.

### 4.5. Статистика

- `rule_id`: `components.add_provided_by`.
- `count`: число компонентов, у которых свойство было добавлено или заполнено
  (один компонент — максимум единица, независимо от числа совпавших строк).
- Правило включено по умолчанию, поэтому при стандартных настройках в
  статистике появляется дополнительная строка (8 статических строк вместо 7).
- При пустом наборе активных строк правило включено, но всегда даёт `count = 0`.

## 5. API и хранение настроек

`GET /api/v1/sbom/fix/options` возвращает новые поля автоматически через
`model_dump()`. `POST /api/v1/sbom/fix/options` валидирует их через
`SbomFixOptions.model_validate`; элемент `provided_by_patterns` неверного типа
даёт `400 invalid_options`, пустые строки внутри набора допустимы и
игнорируются правилом. `POST /api/v1/sbom/fix` принимает те же опции в
JSON-строке `options`.

Файл настроек `./data/sbom_fix_options.json` хранит новые ключи внутри блока
`components`. Старый сохранённый файл без этих ключей дополняется значениями
по умолчанию Pydantic: правило включено, есть стартовая строка Astra. Явно
сохранённый пустой `provided_by_patterns: []` остаётся пустым. Миграции и
обратной совместимости сверх поведения Pydantic по умолчанию нет.

## 6. UI

### 6.1. Каталог правил и типы

- `frontend/src/types/api.ts`: новый интерфейс
  `ProvidedByPatternItem { field: string; pattern: string; provided_by: string }`;
  в `ComponentsFixOptions` — `add_provided_by: boolean` и
  `provided_by_patterns: ProvidedByPatternItem[]`.
- `ComponentsRuleKey = Exclude<keyof ComponentsFixOptions, 'provided_by_patterns'>`.
- `frontend/src/views/sbomFixerRules.ts`: новое правило
  `components.add_provided_by` с ключом `add_provided_by` после
  `fill_missing_gost_properties`, с before/after примером: компонент с
  `purl: "pkg:deb/astra/..."` до и с
  `properties: [{"name": "GOST:provided_by", "value": "..."}]` после.
- `ALL_FIX_RULES` автоматически включает новое правило.

### 6.2. Редактор строк

Под строкой нового правила в карточке `components` рендерится локальный блок:

- на каждую строку — три `input`: поле, значение, название СЗИ;
- подпись между первым и вторым полем — «содержит»;
- кнопка удаления строки и кнопка «Добавить строку»;
- все инпуты и кнопки недоступны, пока `options.components.add_provided_by`
  выключен; при выключении правила введённые строки сохраняются в состоянии;
- пустой сохранённый список отображается одной пустой строкой (как у
  Proprietary);
- атрибуты для тестов: `data-provided-by-row`, `data-provided-by-field`,
  `data-provided-by-value`, `data-provided-by-name`,
  `data-action="add-provided-by"`, `data-action="remove-provided-by"`.

Состояние `providedByRows` инициализируется стартовой строкой Astra. При
загрузке настроек строки клонируются из `options.components.provided_by_patterns`;
пустой массив превращается в одну пустую строку. При сохранении и запуске
исправления все три поля обрезаются по пробелам, строки с пустым любым полем
отбрасываются. `restoreDefaults()` возвращает стартовую строку Astra. Watch на
`providedByRows` участвует в том же механизме отслеживания несохранённых
изменений, что и `patternRows`.

### 6.3. Тексты

Русская локаль:

- имя правила: «Добавить свойство GOST:provided_by для компонентов со
  следующими признаками:»;
- подсказки полей: «Поле», «содержит», «Значение», «Название
  сертифицированного СЗИ»;
- кнопки: «Добавить строку», «Удалить строку»;
- help-панель: описывает подстроку с учётом регистра, первое совпадение
  сверху вниз, пропуск компонентов с непустым `GOST:provided_by`, заполнение
  пустого значения, область `components[]`, отсутствие влияния на
  `metadata.component`.

Английская локаль получает зеркальные тексты.

## 8. Тесты

Backend (`tests/test_sbom_fixer.py`, `tests/test_sbom_fix_api.py`,
`tests/test_sbom_fix_options_store.py`):

- значения по умолчанию: правило включено, ровно одна стартовая строка;
- совпадение по `purl` (подстрока), добавление свойства;
- рекурсивный обход вложенных `components[]`, `metadata.component` не
  затрагивается;
- первое совпадение сверху вниз при нескольких подходящих строках;
- строка с пустым `provided_by` игнорируется;

- отсутствующий/`null` `properties` создаётся, нестроковый — пропускается;
- пустой набор строк — `count = 0`;

- компонент со свежим `GOST:provided_by` не получает
  `component.missing_source_reference`;
- API: GET/POST опций, сохранение и загрузка, неверный тип элемента → 400;
- старый файл настроек без новых ключей получает значения по умолчанию.

Frontend (`frontend/src/views/SbomFixer.test.ts`,
`frontend/src/views/sbomFixerRules.test.ts`):

- `restoreDefaults()` возвращает стартовую строку Astra.

## 9. Риски и известные следствия

- Правило включено по умолчанию, поэтому поведение кнопки «Исправить» при
  стандартных настройках меняется: компоненты Astra получат свойство и перестанут
  требовать ссылку на исходные тексты. Это и есть цель задачи; изменение
  фиксируется в specs.
- Старый файл настроек, сохранённый до появления правила, загрузится с
  включённым правилом и строкой Astra. Если пользователю это не нужно, он
  выключает пункт и сохраняет настройки.
- Свойство `GOST:provided_by` не проверяется на соответствие сертификату и
  составу среды функционирования: правило доверяет настройкам пользователя.
- Строки с пустым названием СЗИ молча игнорируются; в UI нет отдельной
  валидации, кроме отбрасывания при сохранении.
