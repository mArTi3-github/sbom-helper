1. SBOM-оркестрация в router.py — обмельчание Service Layer

Strong

Файлы: router.py:58-119, service.py, sbom/*.py

Проблема: Вся оркестрация SBOM-обработки (парсинг → сбор PURL → дедупликация → батч-резолвинг → обогащение → отчёт) зашита прямо в HTTP-обработчик resolve_sbom_endpoint(). Это 60 строк операционной логики в маршруте.

Before — оркестрация в router.py

flowchart LR
    HTTP(["POST /api/v1/resolve/sbom"]) --> R[router.py]
    R --> P[sbom/parser.py]
    R --> C[sbom/collector.py]
    R --> D[дедупликация inline]
    R --> S[service.resolve_purl ×N]
    R --> E[sbom/enricher.py]
    R --> Rp[sbom/reporter.py]

    style R fill:#fca5a5,stroke:#991b1b
    style D fill:#fca5a5,stroke:#991b1b

After — выделенный Service Layer

flowchart LR
    HTTP(["POST /api/v1/resolve/sbom"]) --> R[router.py]
    R --> SVC[service.process_sbom]
    SVC --> P[sbom/parser.py]
    SVC --> C[sbom/collector.py]
    SVC --> Br[service.resolve_batch]
    SVC --> E[sbom/enricher.py]
    SVC --> Rp[sbom/reporter.py]

    style R fill:#bbf7d0,stroke:#166534
    style SVC fill:#bbf7d0,stroke:#166534

Решение

Выделить функцию process_sbom(sbom: dict, storage: Storage, resolvers: list[Resolver]) -> dict в service.py, переиспользовав существующий паттерн. Добавить resolve_batch(purls: list[str], ...) для группового резолвинга. router.py сводится к 3 строкам: прочитать файл → вызвать service → вернуть JSON.

Преимущества

  • Locality: баги в SBOM-логике ищутся в одном месте — не надо пробираться через HTTP-слой
  • Leverage: process_sbom() тестируется через Service Layer без HTTP; resolve_batch() переиспользуется для API и CLI в будущем
  • Seam: появляется явный интерфейс между HTTP и SBOM-логикой

Deletion test: удаление router.py оставит без HTTP, но логика SBOM выживет. Удаление service.py сейчас оставит без оркестрации — он зарабатывает свою глубину.

2. Троекратное дублирование _normalize_purl

Strong

Файлы: sbom/enricher.py:6-12, sbom/reporter.py:6-12, purl_utils/__init__.py:39-42

Проблема: Одна и та же функция _normalize_purl() (импортирует validate + normalize, обрабатывает Exception, возвращает purl как есть при ошибке) написана трижды: в enricher.py, reporter.py, и встроена в router.py:96-97. Это классическая эрозия интерфейса — каждый модуль сам решает, как нормализовать PURL.

Current

# enricher.py
def _normalize_purl(purl):
    from ..purl_utils import validate, normalize
    try: return normalize(validate(purl))
    except: return purl

# reporter.py  (identical copy)
def _normalize_purl(purl):
    from ..purl_utils import validate, normalize
    try: return normalize(validate(purl))
    except: return purl

# router.py  (inline)
n = normalize(validate(comp.purl))

Fixed

# purl_utils/__init__.py
def safe_normalize(purl: str) -> str:
    try: return normalize(validate(purl))
    except: return purl

# enricher.py, reporter.py, router.py
from ..purl_utils import safe_normalize

Решение

Добавить safe_normalize(purl: str) -> str в purl_utils/__init__.py и импортировать везде. Это не меняет поведение — просто устраняет дублирование.

Преимущества

  • Leverage: один вызов вместо 3 копий одной логики
  • Locality: если поведение safe_normalize нужно изменить (например, логировать ошибки парсинга) — меняется в одном месте
  • Тесты: тестируется однократно в test_purl_utils.py, а не неявно в каждом модуле

Deletion test: удаление любой из трёх копий _normalize_purl не удалит функциональность — она есть в двух других модулях. Это признак, что модуль не зарабатывает своё существование.

3. Нет batch-резолвинга — PURL резолвятся по одному

Worth exploring

Файлы: router.py:105-111, service.py

Проблема: SBOM-эндпоинт резолвит PURL в цикле for original, normalized in unique_purls: result = await resolve_purl(...). Каждый вызов — отдельная корутина с lookup в БД + вызов резолвера. Нет возможности распараллелить (asyncio.gather), нет единого логирования прогресса, нет лимита на batch. При 1000 PURL в SBOM время обработки = последовательная сумма Latency × 1000.

Before — последовательный цикл

flowchart LR
    R["router.py"] --> P1["resolve_purl(purl_1)"]
    R --> P2["resolve_purl(purl_2)"]
    R --> P3["resolve_purl(purl_3)"]
    R --> PN["...resolve_purl(purl_N)"]

    style R fill:#fca5a5,stroke:#991b1b

After — batch-функция

flowchart LR
    S["service.resolve_batch()"] --> G["asyncio.gather(resolve_purl(…), …)"]
    S --> L[логирование прогресса]
    S --> R["dict[norm_purl → repo_url]"]

    style S fill:#bbf7d0,stroke:#166534

Решение

Добавить async def resolve_batch(purls: list[str], storage, resolvers) -> dict[str, str] в service.py, использующую asyncio.gather() для параллельных запросов. Лимит параллелизма через semaphore (например, 10 concurrent).

Преимущества

  • Leverage: batch-резолвинг пригодится не только SBOM, но и будущему POST /api/v1/resolve/batch (запланирован в project_plan.md)
  • Locality: управление конкурентностью, таймаутами и логированием в одном месте
  • Тесты: тест с FakeResolver + 10 PURL проверяет, что все разрешились, без HTTP
Note: не противоречит ни одному ADR. project_plan.md п. 3 ("Пакетная обработка PURL") явно предполагает этот эндпоинт в будущем.

4. CycloneDXParser — класс без состояния

Speculative

Файлы: sbom/parser.py

Проблема: CycloneDXParser — класс с одной константой и одним classmethod. Никогда не инстанциируется, не хранит состояние. Это добавляет церемонию (класс) без выгоды (состояние, полиморфизм). Модульная функция parse_cyclonedx() была бы проще и Pythonic.

Current

class CycloneDXParser:
    SUPPORTED_VERSIONS = {"1.6"}

    @classmethod
    def parse(cls, data): ...

Simpler

SUPPORTED_VERSIONS = {"1.6"}

def parse_cyclonedx(data): ...

Решение: заменить класс на модульные константы + функцию. Это косметическое улучшение, не меняет поведение. Deletion test: класс — чистый namespace; удаление класса не перемещает сложность, а просто убирает обёртку.

Топ-рекомендация

Начать с Candidate 1 (выделение SBOM-оркестрации в Service Layer) — это даёт наибольший выигрыш:

  • Немедленно делает SBOM-логику тестируемой без HTTP (сейчас 0 unit-тестов на оркестрацию)
  • Попутно устраняет Candidate 3 (естественным образом рождается resolve_batch())
  • Не требует переписывания существующих модулей — только перемещение кода
  • Следует существующему паттерну service.py, который уже зарекомендовал себя
