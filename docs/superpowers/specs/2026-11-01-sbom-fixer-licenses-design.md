# «Исправить SBOM» — подраздел «Правки, касающиеся лицензий компонентов»: дизайн

Документ дополняет `2026-10-26-sbom-fixer-design.md`, `2026-10-29-sbom-fixer-optional-fields-design.md`, `2026-10-29-sbom-fixer-rule-help-design.md` и `2026-11-01-sbom-fixer-base-fixes-group-design.md` в части состава статических правил, модели опций и интерфейса. При расхождениях приоритет у этого документа.

## 1. Задача и зачем

Требования ФСТЭК (`.misc/addictional_materials/sbom_description_fstec.md`, таблица П.5, поле `externalReferences`) разрешают не указывать ссылку на исходный код (`vcs` или `source-distribution`), если компонент не является открытым и в его `licenses` есть запись с полем `name`, равным «Proprietary». Сейчас «Исправить SBOM» не умеет ни привести массив лицензий к этому виду, ни воспользоваться получившимся исключением: ссылки на исходники остаются, а несоответствие `component.missing_source_reference` продолжает фиксироваться.

Нужно добавить в раздел «Исправить SBOM» новый подраздел **«Правки, касающиеся лицензий компонентов»** с тремя пунктами:

1. удаление всех записей лицензий, не являющихся «Proprietary» (по умолчанию выключено);
2. добавление записи `{"license": {"name": "Proprietary"}}` компонентам, совпавшим по настраиваемому списку пар «поле — значение» (по умолчанию выключено);
3. удаление из `externalReferences` элементов с `type` = `vcs` или `source-distribution` у компонентов с проприетарной лицензией (по умолчанию выключено).

У каждого пункта — справочная кнопка «(?)» с описанием и примером «До/После», как у остальных правил раздела.

## 2. Цели, не-цели и анти-цели

### Цели

- Три новых статических правила с отдельными rule id, флагами и строками статистики.
- Список пар «поле — значение» редактируется в интерфейсе построчно и сохраняется на сервере вместе с остальными опциями фиксера.
- Лицензии добавляются и удаляются до проверки необходимости ссылок на исходный код; правило удаления ссылок выполняется после добавления лицензий.
- Новый подраздел в UI с мастер-чекбоксом и кнопками «Выбрать всё» / «Снять всё», со справкой «(?)» у каждого пункта.
- Обновлены backend- и frontend-тесты, локализация en/ru и project specs.

### Не-цели

- Не трогать `metadata.component.licenses` — правила работают только с деревом `components[]`.
- Не добавлять новых endpoint'ов: список пар и флаги живут в существующих `SbomFixOptions` и сохраняются существующей кнопкой «Сохранить настройки».
- Не менять логику сбора несоответствий, анализа необязательных полей, белых списков и существующих правил.
- Не менять список «Игнорировать компоненты с перечисленными признаками» в разделе «Обогатить SBOM» и не выносить его редактор в общий компонент.
- Не поддерживать устаревшие формы опций специальным кодом: отсутствующий блок `licenses` в старом `data/sbom_fix_options.json` просто получает значения по умолчанию.
- Не делать сопоставление значений регистронезависимым и не поддерживать составные пути вида `manufacturer.name`.

### Анти-цели

- Удалять ключ `externalReferences` целиком, когда массив опустел.
- Считать проприетарной запись с `license.id`, `expression` или `name` на верхнем уровне элемента массива.
- Заменять существующие записи лицензий при добавлении Proprietary.
- Добавлять повторную запись Proprietary компоненту, у которого она уже есть.
- Включать новые правила по умолчанию.
- Делать отдельную кнопку сохранения списка внутри подраздела или отдельный эндпоинт.
- Дублировать проход по документу три раза, если хватает одного обхода.

## 3. Ограничения и допущения

- Backend: FastAPI + Pydantic, stdlib; frontend: Vue 3 `<script setup>`, Pinia, vue-i18n.
- Все пользовательские строки — через i18n (`ru`, `en`).
- `fix_sbom()` не мутирует входной документ (работает на `copy.deepcopy`) и остаётся однопроходным по дереву компонентов.
- Python-код запускается в `.venv`; frontend-проверки — `npm --prefix frontend`.
- Сопоставление по списку повторяет семантику обогащения (`src/purl_resolver/sbom_enrichment.py:29`): проверяется поле верхнего уровня компонента; если поля нет или его значение `null`, пара не совпадает; иначе совпадение ищется вхождением подстроки в `str(value)`; достаточно любой пары. Пары, у которых `field` или `pattern` пусты после `strip()`, игнорируются и на фронтенде, и на бэкенде.
- Сравнение названия лицензии — точное и регистрозависимое: `"Proprietary"`.
- Массив `licenses` может содержать элементы `{"license": {...}}` и `{"expression": "..."}`; проприетарным считается только первый вид с `license.name == "Proprietary"`.
- Порядок выполнения правил фиксирован; сборка `issues` уже происходит после всех правок (`fixer.py`, конец `fix_sbom`), менять это не нужно.

## 4. Рассмотренные подходы

### Подход 1 — всё внутри фиксера (выбран)

`SbomFixOptions` получает вложенный блок `licenses: LicensesFixOptions` с тремя флагами и списком пар. Пары сохраняются на сервере тем же механизмом, что и остальные опции (`SbomFixOptionsStore` → `data/sbom_fix_options.json`), списком в `GET/POST /api/v1/sbom/fix/options`. Новый подраздел UI — четвёртая карточка на странице с инлайн-редактором строк.

Плюсы: серверное хранение появляется без нового кода; одна кнопка сохранения и один источник истины; нет новых эндпоинтов, store и API-методов; наименьший diff. Минусы: у списка нет собственной кнопки сохранения, как у списка игнорирования в «Обогатить SBOM», и общий payload опций растёт.

### Подход 2 — отдельный ресурс для списка пар

Флаги — в `SbomFixOptions`, пары — в отдельном эндпоинте и store по образцу `ignore_patterns_store.py`, со своей кнопкой сохранения в подразделе.

Плюсы: UX буквально как в «Обогатить SBOM»; список живёт независимо от прочих опций. Минусы: новый store, роут, методы API и ещё один поток сохранения на странице; два источника истины и больший объём тестов. Отклонён.

### Подход 3 — вынести редактор пар в общий компонент

Извлечь разметку и стили редактора из `SbomUpdater.vue` в компонент и переиспользовать в `SbomFixer.vue`.

Плюсы: одна реализация редактора. Минусы: затрагивает работающую страницу «Обогатить SBOM», её стили и тесты ради ~15 строк; не требуется задачей. Отклонён: редактор пишется инлайн в `SbomFixer.vue`.

**Решение:** подход 1, редактор пар — инлайн.

## 5. Модель опций и API

### 5.1. Backend

```python
class LicensePatternItem(BaseModel):
    field: str = ""
    pattern: str = ""

class LicensesFixOptions(BaseModel):
    filter_non_proprietary: bool = False
    add_proprietary: bool = False
    remove_proprietary_source_references: bool = False
    add_patterns: list[LicensePatternItem] = Field(default_factory=list)

class SbomFixOptions(BaseModel):
    # существующие поля без изменений
    ...
    components: ComponentsFixOptions = Field(default_factory=ComponentsFixOptions)
    licenses: LicensesFixOptions = Field(default_factory=LicensesFixOptions)
    optional_fields: OptionalFieldsFixOptions = Field(default_factory=OptionalFieldsFixOptions)
```

- Отдельный валидатор для `add_patterns` не нужен: неверный тип списка или элемента отклоняется стандартной валидацией Pydantic и превращается в `400 invalid_options` существующим путём.
- Неполные пары (пустое после `strip()` значение `field` или `pattern`) допустимы: они пропускаются при применении правила, как пустые правила игнорирования в обогащении. Отдельная нормализация при сохранении не нужна: модель хранит пары как есть, а правило отбрасывает неполные.
- `_rule_enabled` расширяется: id с префиксом `licenses.` читает поле из `options.licenses`, id с префиксом `components.` — из `options.components`, остальные — из корня.
- `RULE_IDS` становится кортежем из 11 значений; три новых идут после правил `components`, в порядке применения:

```python
RULE_IDS = (
    "reorder",
    "set_spec_version",
    "increment_version",
    "add_timestamp",
    "add_manufacturer",
    "components.filter_external_references",
    "components.filter_properties",
    "components.fill_missing_gost_properties",
    "licenses.filter_non_proprietary",
    "licenses.add_proprietary",
    "licenses.remove_proprietary_source_references",
)
```

### 5.2. JSON опций

`POST /api/v1/sbom/fix` (поле `options`), `GET/POST /api/v1/sbom/fix/options` получают дополнительный блок:

```json
{
  "licenses": {
    "filter_non_proprietary": false,
    "add_proprietary": false,
    "remove_proprietary_source_references": false,
    "add_patterns": [
      { "field": "name", "pattern": "vendor-lib" }
    ]
  }
}
```

Файл `data/sbom_fix_options.json` получает тот же блок. Старый файл без него читается без ошибок: все флаги `false`, список пуст.

### 5.3. Frontend-типы

В `frontend/src/types/api.ts`:

- новый интерфейс `LicensesFixOptions` с тремя `boolean` и `add_patterns: IgnorePatternItem[]` (существующий тип `IgnorePatternItem` переиспользуется, дубликат не создаётся);
- `SbomFixOptions` получает поле `licenses: LicensesFixOptions`.

`SbomFixStat`, `SbomFixIssue` и `SbomFixResponse` не меняются.

## 6. Правила

Общий предикат:

```python
def _has_proprietary_license(component: dict) -> bool:
    licenses = component.get("licenses")
    return isinstance(licenses, list) and any(
        isinstance(entry, dict)
        and isinstance(entry.get("license"), dict)
        and entry["license"].get("name") == "Proprietary"
        for entry in licenses
    )
```

Обход — существующая `_walk_components(data, ...)`: дерево `components[]` на любой глубине, `metadata.component` не затрагивается.

### 6.1. `licenses.filter_non_proprietary` — «Удалить все лицензии без поля с ключом `name`, равным «Proprietary»»

Для каждого компонента:

- если `licenses` не список — компонент не меняется, счётчик не растёт;
- иначе остаются только элементы, для которых `entry.license.name == "Proprietary"`;
- если удалён хотя бы один элемент: при непустом остатке `component["licenses"] = kept`, при пустом — ключ `licenses` удаляется целиком;
- если элементов не было вовсе (пустой массив), массив остаётся как есть;
- `count` = число удалённых элементов массива (не число компонентов и не удалённые ключи).

### 6.2. `licenses.add_proprietary` — «Добавить лицензию с ключом `name`, равным «Proprietary» для компонентов со следующими признаками:»

Список пар берётся из `options.licenses.add_patterns`; пары с пустым `field` или `pattern` отбрасываются. Если после отбрасывания список пуст, правило ничего не делает.

Для каждого компонента:

- совпадение — если поле верхнего уровня компонента существует и его значение не `null`, и для хотя бы одной пары `pattern in str(value)`; пары предварительно обрезаются по краям, пустые отбрасываются. Отсутствующее поле и `null` не совпадают ни с чем: иначе короткий шаблон вроде `no` совпал бы со строкой `None` у компонентов без этого поля;
- если компонент не совпал или уже имеет проприетарную запись — изменений нет;
- если `licenses` отсутствует или равно `null` — создаётся пустой массив; если присутствует и не является списком — компонент пропускается без перезаписи;
- в конец массива добавляется `{"license": {"name": "Proprietary"}}`;
- `count` = число компонентов, которым добавлена запись.

Существующие записи (в том числе `license.id` и `expression`) сохраняются; смешанный массив допустим, так как требования ФСТЭК проверяют только наличие Proprietary-записи.

### 6.3. `licenses.remove_proprietary_source_references` — «Удалить ссылки `vcs` и `source-distribution` у компонентов с проприетарной лицензией»

Для каждого компонента:

- применяется только при `_has_proprietary_license(component)`;
- если `externalReferences` не список или отсутствует — компонент не меняется;
- из списка удаляются только элементы-объекты с `type` = `vcs` или `source-distribution` (точное сравнение); остальные элементы, включая не-объекты, сохраняются;
- при удалении хотя бы одного элемента массив записывается обратно, даже если стал пустым (`"externalReferences": []`); ключ никогда не удаляется;
- `count` = число удалённых элементов массива.

Правило не удаляет `metadata.component.externalReferences`.

### 6.4. Порядок выполнения

В `fix_sbom()` после `_apply_components_rules` вызывается `_apply_licenses_rules`, затем `_apply_reorder`, затем собираются `issues`. Внутри `_apply_licenses_rules` для каждого компонента шаги применяются в фиксированном порядке: удаление не-Proprietary → добавление Proprietary → удаление ссылок. Поскольку состояние компонентов не зависит друг от друга, один обход дерева эквивалентен трём последовательным и дешевле на больших файлах.

Следствие: компонент, которому правило добавления проставило Proprietary, сразу попадает под правило удаления ссылок, а сборка `issues` видит уже итоговые `licenses` и `externalReferences`.

### 6.5. Статистика

- Три новые строки в порядке `RULE_IDS`, после строк правил `components`.
- Единицы измерения: удалённые записи лицензий, компоненты с добавленной записью, удалённые внешние ссылки.
- Если правило включено, строка показывается и при нулевом счётчике — как у существующих правил; выключенные правила в статистику не попадают.
- Подпись строки — существующий `statLabel()` через `t('sbomFixer.rules.' + stat.rule_id)`, поэтому ключи i18n вложены в `rules.licenses.*`.

## 7. Интерфейс

Новая карточка `data-group="licenses"` размещается между «Правки массива components[]» и «Удаление необязательных полей по „белому списку“»: это единственная позиция, где относительный порядок карточек совпадает с порядком выполнения (существующие карточки строгому порядку не соответствуют: `reorder` показан первым, но выполняется последним; удаление необязательных полей выполняется первым, но показано последним).

### 7.1. Состав карточки

Заголовок — «Правки, касающиеся лицензий компонентов» / «Component license edits». Мастер-чекбокс управляет тремя флагами и не трогает список пар; рядом — «Выбрать всё» / «Снять всё», как в других карточках.

| # | Rule id | Пункт (ru) | Дополнительный контрол |
|---|---|---|---|
| 1 | `licenses.filter_non_proprietary` | Удалить все лицензии без поля с ключом `name`, равным «Proprietary» | — |
| 2 | `licenses.add_proprietary` | Добавить лицензию с ключом `name`, равным «Proprietary» для компонентов со следующими признаками: | построчный редактор пар под пунктом |
| 3 | `licenses.remove_proprietary_source_references` | Удалить ссылки `vcs` и `source-distribution` у компонентов с проприетарной лицензией | — |

У каждого пункта — `RuleHelp` с описанием и примером «До/После».

### 7.2. Редактор пар

- Строка: текстовое поле «Поле», слово «содержит», текстовое поле «Значение», кнопка удаления строки.
- Под строками — кнопка «Добавить строку».
- Если сохранённый список пуст, показывается одна пустая строка (как в `SbomUpdater.vue`).
- Поля и кнопки редактора неактивны, пока выключен пункт `add_proprietary` (как текстовое поле «Производитель» при выключенном `add_manufacturer`); строки при выключении не очищаются.
- Перед сохранением и перед отправкой на исправление строки с пустым полем или пустым значением отбрасываются и обрезаются по краям; пустые пары на сервер не уходят.

### 7.3. Связь с опциями

- Каталог правил `frontend/src/views/sbomFixerRules.ts` получает `LICENSES_RULES` (3 записи: id, ключ флага, пример до/после) и тип `LicensesRuleKey` (три булевых ключа без `add_patterns`) по образцу `COMPONENTS_RULES`.
- `SbomFixer.vue` хранит строки редактора отдельным реактивным списком, как `patternRows` в `SbomUpdater.vue`; `applyOptions()` заполняет его из `options.licenses.add_patterns`, `plainOptions()` кладёт нормализованный список обратно.
- Мастер-чекбокс и «частично выбрано» считаются по трём флагам, как в существующих карточках.
- `restoreDefaults()` сбрасывает три флага в `false` и оставляет одну пустую строку, значения из сохранённых опций не подставляются.

## 8. Локализация

`frontend/src/i18n/locales/{ru,en}.json`, пространство `sbomFixer`:

- `groups.licenses` — «Правки, касающиеся лицензий компонентов» / «Component license edits»;
- `rules.licenses.filter_non_proprietary`, `rules.licenses.add_proprietary`, `rules.licenses.remove_proprietary_source_references` — названия из таблицы 7.1;
- `help.licenses.*` — описания: что считается проприетарной записью, что происходит с опустевшим массивом и с массивом `externalReferences`, как сопоставляются признаки и что пустые пары игнорируются;
- `licenses.contains`, `licenses.fieldPlaceholder`, `licenses.valuePlaceholder`, `licenses.addRow`, `licenses.removeRow` — подписи редактора пар; текст «содержит» / «contains» совпадает по смыслу с редактором в «Обогатить SBOM».

Существующие ключи не переименовываются.

## 9. Тесты

Backend (`tests/test_sbom_fixer.py`, `tests/test_sbom_fix_options_store.py`, `tests/test_sbom_fix_api.py`):

- значения по умолчанию: три флага `false`, `add_patterns == []`; состав и порядок `RULE_IDS` из 11 id;
- удаление: остаются только Proprietary-записи; `license.id` и `expression` удаляются; вложенные компоненты обрабатываются; опустевший массив удаляется; уже пустой массив не трогается; `licenses` не-список не меняется; счётчик равен числу удалённых записей;
- добавление: совпадение по любой паре; сравнение вхождением подстроки; отсутствующее поле и `null` не совпадают; пары из одних пробелов игнорируются; отсутствующий массив и `licenses: null` создаются как массив; существующая Proprietary-запись не дублируется; `licenses` не-список пропускается; счётчик равен числу компонентов;
- удаление ссылок: удаляются только `vcs` и `source-distribution`; прочие типы и не-объекты остаются; массив остаётся пустым, а не удаляется; компонент без Proprietary не меняется; `metadata.component.externalReferences` не затрагивается; счётчик равен числу удалённых ссылок;
